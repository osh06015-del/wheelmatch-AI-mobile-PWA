# 안전 앱 공통 규칙

사람이 다치는 판단을 내리는 앱에 공통으로 적용한다. **앱이 달라도 이 8개는 같다.**

각 규칙은 "무엇을" + "왜" + "이 저장소에서 어디에" 순으로 적는다.
이 저장소의 구체적 구현·경계값은 [safety-invariants.md](safety-invariants.md),
OCR 계층은 [vision-ocr.md](vision-ocr.md)에 있다. 중복해서 적지 않는다.

---

## 1. 인식과 판정을 분리한다

모델은 **값을 읽기만** 한다. 적합/부적합을 말하지 않는다.
판정은 외부 의존성 없는 순수 함수 한 곳에서만 한다.

**왜:** 모델은 그럴듯한 문장을 만들도록 학습돼 있다. 판정을 시키면 근거 없이
"안전합니다"를 만들어낼 수 있고, 그것을 사후에 검증할 방법이 없다.
규칙은 읽고 셀 수 있어야 한다.

**여기서는:** `src/lib/rules/engine.ts`. `eslint.config.mjs`의
`boundary/rules-engine-purity`가 이 파일의 import를 막아 강제한다.

## 2. 원본·정규화·판정근거를 따로 보관한다

세 가지를 **각각** 남긴다. 덮어쓰지 않는다.

| 무엇                | 이 저장소                                        |
| ------------------- | ------------------------------------------------ |
| 모델이 읽은 원본    | `InspectionRecord.grinderOcr` / `.wheelOcr`      |
| 사용자 확인 후 최종 | `.grinder` / `.wheel`                            |
| 판정 근거           | `.result.checks[]` (규칙명·통과여부·사유·양쪽값) |

**왜:** 셋을 합치면 "모델이 틀렸는지, 사람이 고쳤는지, 규칙이 어떻게 판단했는지"를
나중에 되짚을 수 없다. 사고가 났을 때 되짚지 못하는 기록은 기록이 아니다.
인식률·정정률 같은 지표도 원본이 남아 있어야 계산된다.

## 3. 값이 없거나 서로 충돌하면 판정을 보류한다

핵심 필드가 비었으면 **판정불가**다. 통과가 아니다.
서로 다른 경로에서 읽은 값이 충돌해도 판정불가다.

**왜:** 빈 값을 기본값으로 채우면 그 순간 근거 없는 통과가 만들어진다.
"모르겠다"를 말할 수 있는 앱만 믿을 수 있다.

**여기서는:** 읽지 못한 값은 `null`. `decideVerdict()`가 `null`을 `UNDETERMINED`로
올린다. 값이 서로 어울리지 않는 경우(자릿수 오독)는 `checkPeripheralSpeed()`가
잡아 역시 판정불가로 내린다.

## 4. confidence가 낮으면 자동으로 안전 판정하지 않는다

모델이 스스로 낮다고 말한 결과를 통과시키지 않는다.
낮은 신뢰도를 푸는 방법은 **사람이 직접 확인하는 것뿐**이다.

**왜:** 신뢰도는 모델이 주는 유일한 자기 경고다. 무시하면 그 신호를 받는 의미가 없다.

**여기서는:** `checkConfidence()`가 `low`를 판정불가로 만든다.
`ManualConfirmToggle`로 사람이 확인해야 `high`로 올라간다. 코드가 임의로 올리지 않는다.

## 5. 법적 인증이나 전문가 검사를 대체한다고 말하지 않는다

화면 문구·문서·발표 자료 어디에도 이렇게 쓰지 않는다.

- ❌ "안전합니다" / "사용해도 됩니다" / "검사 완료"
- ✅ "표시된 규격끼리는 서로 맞습니다"

**왜:** 이 앱은 라벨에 **적힌 값**만 본다. 숫돌의 실제 상태, 기계 마모, 작업 방법을
보지 못한다. 승인처럼 읽히는 문구 하나가 작업자의 다른 확인 절차를 없앤다.

번역할 때 특히 조심한다 — 영어 `verdict.compatible`을 `OK to use`가 아니라
`SPECS MATCH`로 쓴 이유다. 자세한 경계는 [docs/safety-boundaries.md](../../docs/safety-boundaries.md).

## 6. 규정 데이터에는 출처를 기록한다

법령·표준에서 가져온 숫자나 문구를 코드에 넣을 때는 **네 가지를 함께** 남긴다.

1. **관할 국가** (KR / US / EU …)
2. **출처 URL**
3. **문서 버전 또는 조항 번호**
4. **시행일**

확인하지 못한 항목은 비워 두고 `미확인`이라고 적는다. **지어내지 않는다.**

**왜:** 법령은 개정된다. 출처 없는 숫자는 개정 시 찾을 수 없고, 틀렸을 때
어디서 왔는지도 모른다. 안전 기준을 추측으로 인용하는 것이 기준이 없는 것보다 나쁘다.

**여기서는:** [docs/regulatory-sources.md](../../docs/regulatory-sources.md)에 표로 모은다.
코드 주석에는 조항 번호만 적고 상세는 그 문서를 가리킨다.

## 7. 판정 로직을 바꾸면 테스트를 함께 추가한다

규칙 함수를 추가·수정·삭제할 때 테스트가 같은 커밋에 들어간다.
**기존 경계값 테스트를 통과시키려고 기대값을 낮추지 않는다.** 코드를 고친다.

**왜:** 판정 로직의 회귀는 화면에서 보이지 않는다. 부적합이 적합으로 바뀌어도
앱은 멀쩡히 돌아간다. 테스트가 유일한 감지 수단이다.

**여기서는:** `src/lib/rules/*.test.ts`. 작성 방식은 [testing.md](testing.md).

## 8. 이미지와 전체 인식 텍스트를 로그에 남기지 않는다

production 로그에 다음을 넣지 않는다.

- 촬영 원본·축소본 이미지, base64 문자열
- OCR이 읽은 **전체 텍스트**(`rawText`)
- API 키, 토큰, 요청 본문 전체

남겨도 되는 것: 상태 코드, 오류 종류, 오류 메시지, 처리 시간, 필드별 성공 여부.

**왜:** 현장 사진에는 작업자·사업장·설비가 찍힌다. 라벨 전문에는 사업장을 식별할
정보가 섞일 수 있다. 이 앱은 기록을 **기기 안에만** 두는 설계인데, 로그로 새면
그 설계가 무의미해진다.

**여기서는:** `src/app/api/extract/route.ts`가 `error.status`와 `error.message`만
남긴다. 이 상태를 유지한다. 디버깅이 필요하면 로컬에서 재현한다.
