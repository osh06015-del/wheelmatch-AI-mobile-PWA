### ⚠ 설계를 바꿔야 하는 것 (4건)

**1. "어떤 숫돌을 끼워야 할지" — 추천이 아니라 조건으로**

제품 추천은 제안서가 명시적으로 제외한 **'안전 승인'** 에 다가선다.
대신 명판에서 곧바로 따라 나오는 조건만 적는다.

```
연삭 작업 · GWS 750-125 (11,000rpm, 최대 Φ125mm)
→ 필요한 숫돌 조건
   연삭용 / Φ125mm 이하 / 최고사용회전속도 11,000rpm 이상
```

규칙엔진의 판정 기준을 그대로 뒤집은 것이라 둘이 어긋날 수 없다.
숫돌을 고르기 **전에** 무엇을 봐야 하는지 알려주므로 현장에서 더 유용하다.

**2. 판정 근거 표시 — crop은 불가능**

Claude는 글자의 **좌표를 돌려주지 않는다**. 모델에게 좌표를 물으면 정밀도가
낮아 엉뚱한 영역을 잘라 보여준다. 근거로 만든 화면이 틀린 근거를 보여주면
없느니만 못하다.

대신 `전체 사진 + 읽어낸 원문 + 값 + 출처`로 간다. 추적성은 그대로 성립한다.
진짜 crop이 필요하면 Tesseract 경로에서만 가능하다(bbox를 준다).

**3. OCR 이중검증 — 기권과 불일치를 구분**

실측(`docs/offline-ocr.md`)에서 현장 사진의 Tesseract 결과는 이랬다.

|           | 결과                                      |
| --------- | ----------------------------------------- |
| Claude    | `GWS 750-125` / `11000` / `125` 전부 정확 |
| Tesseract | `BO 0000` / null / null                   |

"불일치하면 차단"을 그대로 넣으면 **현장 사진은 거의 전부 판정불가**가 된다.

| Tesseract    | 처리                         |
| ------------ | ---------------------------- |
| 값 없음      | **기권** — 불일치 아님, 통과 |
| 값 있고 다름 | **불일치** → 판정불가        |
| 값 있고 같음 | 일치                         |

이러면 "두 경로가 충돌하면 판단을 거부한다"는 서사는 살면서 앱이 쓸모를 잃지 않는다.

**4. "오차율" — 두 가지를 구분해야 한다**

| 무엇의 오차인가                              | 필요한 것               | 어디에 쓰나 |
| -------------------------------------------- | ----------------------- | ----------- |
| **안전 여유율** (숫돌 정격 vs 그라인더 속도) | 없음. 지금 값으로 계산  | 작업자 화면 |
| **OCR 정확도 오차율** (읽은 값 vs 실제 값)   | **정답 입력(연구모드)** | 논문        |

앞의 것은 바로 되고, 뒤의 것은 연구모드가 있어야 한다. 둘 다 넣되 화면을 나눈다.
작업자에게 OCR 정확도 통계는 필요 없다.

### ❌ 넣지 않는 것

| 기능                            | 이유                                                         |
| ------------------------------- | ------------------------------------------------------------ |
| AI가 "안전합니다" 승인          | 제안서 방어전략이 무너진다. 금지선                           |
| 사진으로 균열 "없음" 판정       | 미세균열은 사진에 안 보인다. 표준은 타음검사                 |

| 로그인 / 서버 DB                | 기기 안 저장이 이 앱의 설계다                                |

## 다국어 — 반드시 짚을 것

제안서 기대효과에 "외국인 작업자 지원"이 있고, 현재 UI 문자열은 전부 한국어다.
넣는 것은 기술적으로 어렵지 않다.

**문제는 번역 품질이다.**

이 앱의 문장 상당수가 안전 문구다.

> "숫돌 최고사용회전속도가 그라인더 무부하 회전속도보다 낮습니다. 파손·비산 위험이 있습니다."

**안전 문구를 검수 없이 기계 번역으로 내보내면 안 된다.** 잘못 번역된 경고는
경고가 없는 것보다 나쁠 수 있다.

권장 방식:

1. 구조를 먼저 만든다 (문자열 분리 + 언어 전환)
2. **판정 3색(적합/부적합/판정불가)과 행동지침만 우선 번역** — 가장 중요한 문장
3. 그 문장들만 해당 언어 사용자에게 검수받는다
4. 나머지 설명문은 그 다음에

색과 아이콘은 언어와 무관하게 읽히므로, 글자를 못 읽어도 최소한의 정보는 전달된다.
이것이 이 앱이 다국어에서 유리한 점이다.

## QR 코드 — 검증 완료

실제로 QR을 만들어 인쇄·촬영 조건을 흉내 내 확인했다.

|                                  |                                               |
| -------------------------------- | --------------------------------------------- |
| URL                              | 32자, QR 버전 3 (29×29 모듈) — 매우 낮은 밀도 |
| 크기별                           | 80px~400px 전부 디코딩 성공                   |
| 기울임 15°·30° / 저조도 / 노이즈 | 전부 성공                                     |
| **초점 흐림(심함)**              | **실패**                                      |

**오류정정 레벨을 H로 할 것.** 대부분의 QR 생성기 기본값은 M이다.

| 레벨  | 견디는 오염 |
| ----- | ----------- |
| L / M | 5%          |
| Q     | 10%         |
| **H** | **15%**     |

**스캔 후 열리는 브라우저가 더 중요하다.** 카카오톡·네이버 등의 인앱 브라우저는
카메라를 막는 경우가 많다. 다행히 갤러리 업로드 경로가 있어 앱이 죽지는 않지만,
현장에서 바로 찍는 흐름은 막힌다. QR 옆에 이 문구를 함께 인쇄한다.

> 스캔 후 **"기본 브라우저로 열기"** 를 눌러주세요. (카메라 사용)

## 아직 0%인 것 — 제안서가 약속한 검증

여기가 가장 큰 구멍이다. **코드로 채울 수 없다.**

| 제안서 요구                  | 필요한 것        |
| ---------------------------- | ---------------- |
| 기계·숫돌 **20세트** 실측    | 실물 장비 + 촬영 |
| 수기 vs 앱 **소요시간 비교** | 사람이 초시계로  |
| **5~10명 SUS 설문**          | 대상자 섭외      |

주의: 내가 만든 "규칙엔진 테스트 20개"는 제안서의 "20세트"와 **다른 것**이다.
전자는 로직 검증(합성 값), 후자는 실물 촬영 실험이다. 발표에서 섞어 말하면 지적당한다.

**실험 설계 요점:** 판정이 결정론적 규칙이므로 **부적합 탐지 재현율 = 필드 추출 정확도**다.
추출만 맞으면 판정은 항상 맞는다. 재야 할 것은 하나뿐이고,
"판정 오류"와 "인식 오류"를 분리해 보고할 수 있다.

**OCR 정확도 자동 계산이 생각보다 중요하다.** 1주차에 OCR 원본값을 저장하도록
바꿔서 **데이터는 이미 쌓인다.** 하지만 "인식률 몇 %"를 내주지는 않는다.
지금대로면 CSV를 엑셀로 옮겨 손으로 세야 한다. 20세트를 두 번 찍으면 80줄이다.
논문 숫자가 손계산에서 나오면 재현성이 없다.

### 결정만 하면 되는 것 (3건)

1. **불꽃 방향** — 제안서는 체크리스트 5개, 현재는 4개 + 작업 직전 안내다.
   되돌릴지 이대로 갈지.
2. **규칙 버전에 적을 문서** — 후보를 찾았다:
   KOSHA Guide **`M-189-2015` 「휴대형 연삭기 안전작업에 관한 기술지침」**.
   아직 원문을 보지 않았다. 확인하고 쓸 것.
3. **80 m/s 안전 상한** — 지금 넣은 원주속도 검증은 **오독 필터**이지
   안전 한계가 아니다(15~110 m/s). 진짜 안전 상한을 규칙으로 넣으려면
   KS/EN 12413 원문 확인이 먼저다. 안 넣어도 발표는 된다.

### 사람이 해야 하는 것 (코드로 못 채운다)

## 휴대용 그라인더에 맞는가 — 원문 대조 (2026-09-03)

앱이 **휴대용(앵글) 그라인더**의 실제 규격 체계와 맞는지 법령·제조사 자료로 확인했다.

### 결론: 방향은 맞다

| 앱이 하는 것               | 근거                                                                         |
| -------------------------- | ---------------------------------------------------------------------------- |
| 숫돌 최고사용회전속도 대조 | **산업안전보건기준에 관한 규칙 제122조 ④** — 최고사용회전속도 초과 사용 금지 |
| 작업목적↔숫돌용도 대조     | **제122조 ⑤** — 측면 사용 목적이 아닌 숫돌의 측면 사용 금지                  |
| 방호덮개 체크              | **제122조 ①** — 지름 5cm 이상 숫돌에 덮개                                    |
| 숫돌 손상 확인             | **제122조 ③** — 시운전용 숫돌은 작업 전 결함 확인                            |
| 최대 지름 대조             | 보쉬 코리아 앵글그라인더 안전자료                                            |
| **보조손잡이** 체크        | 휴대용 전용 항목이다. 탁상용에는 없다                                        |
| 4/5/7인치 등급             | 앵글그라인더 규격 체계                                                       |

핵심 규칙의 법적 근거가 **제122조 ④항**이라는 것이 이번 확인의 가장 큰 소득이다.
"규칙 버전에 적을 기준 문서" 문제도 이것으로 답이 된다 — KOSHA Guide보다
법령 조항이 직접적이다. (KOSHA Guide `M-189-2015` 「휴대형 연삭기 안전작업에
관한 기술지침」은 보조 근거로 함께 적을 수 있다.)

무부하 회전속도를 기준으로 비교하는 것도 맞다. 부하가 걸리면 속도가 떨어지므로
무부하가 최악의 경우다. 보수적인 쪽으로 비교하고 있다.

### 그런데 휴대용 기준으로 빠진 것이 둘 있다

**1. 내경(H)을 읽지 않는다**

숫돌 라벨은 `외경 × 두께 × 내경`으로 찍혀 있다 (예: `125 × 1.6 × 22.23`).
`schema.ts`의 프롬프트는 이 표기를 알고 있으면서 **가운데 값(두께)까지만 가져오고
내경을 버린다.**

> `thickness: 숫돌 두께(mm). D×T×H 표기라면 가운데 값입니다.`

내경 규격은 10 / 16 / **22.23** / 25.4mm 등으로 갈린다. 앵글그라인더는 대부분
22.23mm다. 내경이 다르면 **애초에 끼워지지 않거나, 억지로 끼우면 편심이 생긴다.**

보쉬 코리아 안전자료는 이렇게 적는다 — _"교체용 휠의 내경이 기계의 스핀들
사이즈와 정확히 맞아야 하며, 맞지 않는 부품은 사용하면 안 됩니다."_
절단석 판매 자료도 "그라인더 규격(인치)과 내경(mm) 확인"을 **기본**으로 든다.

지금 앱은 그 셋 중 둘(지름·회전속도)만 본다.

주의: 그라인더 명판에는 스핀들 규격이 안 적힌다. 그래서 **양쪽을 대조할 수는
없다.** 할 수 있는 것은 (a) 읽어서 보여주기, (b) 앵글그라인더 통례(22.23mm)와
다르면 **경고**로 알리기 — 차단이 아니다. 통례는 규격 대조가 아니므로
판정을 끌어내리면 안 된다.

**2. 시운전(시험운전)을 말하지 않는다**

**제122조 ②** — 작업 시작 전 **1분 이상**, 숫돌 교체 후 **3분 이상** 시험운전을
하고 이상이 있는지 확인해야 한다. **법적 의무다.**

이 앱은 "작업 직전 30초 사전점검 도구"를 자처한다. 작업 직전에 법으로 하게 되어
있는 절차를 말하지 않는 것은 구멍이다. 지금은 위험사항 목록에 _"새로 끼운 숫돌은
공회전으로 먼저 확인한다"_ 로 들어 있는데, **시간이 빠져 있고 기본 접힘이다.**

숫돌을 교체하고 앱을 쓰는 흐름이 대부분이므로 **3분** 쪽이 실제로 걸린다.

### 제안

- 시운전 안내 (1h) — 저장 후 "작업 직전 안내"에 넣는다. 불꽃 방향 안내 옆이다.
  법령 조항을 근거로 문구를 고정한다.
- 내경 추출 + 표시 (2h) — 스키마·타입·확인 화면. 판정에는 넣지 않는다.
- 내경 통례 경고 (1h) — 22.23mm가 아니면 경고. **차단하지 않는다.**

### Grinder Condition Gate 도입 (2026-09-12)

명판 확인과 숫돌 촬영 사이에 장비 상태 Gate가 들어갔다. 흐름은 이제
`작업 목적 → 명판 → GRINDER CONDITION → 숫돌 → WHEEL CONDITION → SPEC →
작업 전 체크리스트`다. 계층 관계는 `safety-boundaries.md`에 있다.

이 Gate에는 **AI 입력이 없다.** 명판 사진으로는 전원선·덮개·손잡이·스핀들을
볼 수 없어서, 의심 경고조차 붙이지 않았다. 장비 전체 촬영 설계가 생기기
전까지는 이대로 둔다.

최종 체크리스트에서 방호덮개·보조손잡이가 빠져 **보호구 하나만 남았다.**
기계는 Grinder Gate, 숫돌은 Wheel Gate가 맡고, 사람에 대한 항목만 남은
것이다. 새 항목(주변환경·작업물 고정·불꽃 방향)으로 채우는 것은 별도 작업이다.

그라인더를 다시 잡으면 장비 상태뿐 아니라 **숫돌 값과 Wheel Condition까지
함께 버린다.** 기계가 달라지면 그 기계로 본 상태도, 그 기계 기준의 규격
대조도 근거를 잃기 때문이다.
