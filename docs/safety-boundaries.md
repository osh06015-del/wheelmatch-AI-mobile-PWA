# 안전 경계 — 이 앱이 하지 않는 것

앱이 **무엇을 하는가**보다 **무엇을 하지 않는가**를 먼저 정한다.
경계가 흐려지면 작업자가 다른 확인 절차를 생략하게 된다.

이 문서는 화면 문구·문서·발표 자료 전체에 적용된다.
코드 규칙은 `.claude/rules/safety-critical.md`에 있다.

---

## 한 문장으로

> 이 앱은 **라벨에 표시된 규격끼리 서로 맞는지**만 대조한다.
> 작업이 안전한지는 말하지 않는다.

---

## 하는 것 / 하지 않는 것

| 한다                                                   | 하지 않는다                               |
| ------------------------------------------------------ | ----------------------------------------- |
| 라벨에 적힌 값을 읽는다                                | 값을 추정하거나 채워 넣는다               |
| 읽은 값끼리 규칙으로 대조한다                          | "안전하다"고 승인한다                     |
| 못 읽으면 판정불가라고 말한다                          | 모르는 것을 통과로 처리한다               |
| 부적합일 때 다음 행동을 알려준다                       | 제품을 추천한다                           |
| 사진으로 숫돌 **종류**를 제안하고 작업자가 고르게 한다 | 사진으로 균열 **없음**을 판정한다         |
| 사진에서 손상이 **의심**되면 경고한다                  | 손상이 안 보인다고 「손상 없음」이라 한다 |
| 명판에 적힌 최대 지름을 읽는다                         | 사진에서 치수를 **측정**한다              |
| 체크리스트 항목을 보여준다                             | 체크리스트를 대신 체크한다                |

## 절대 쓰지 않는 표현

화면·문서·발표 어디에도 쓰지 않는다.

- ❌ 안전합니다 / 사용해도 됩니다 / 안전 확인 완료 / 검사 통과
- ❌ 이 숫돌을 쓰세요 (제품 추천)
- ❌ 균열이 없습니다
- ✅ 표시된 규격끼리는 서로 맞습니다
- ✅ 값이 부족해 판정할 수 없습니다
- ✅ 사진으로는 미세균열을 확인할 수 없습니다. 장착 전 타음검사를 하세요

번역에도 그대로 적용된다. 영어 판정을 `OK to use`가 아니라 **`SPECS MATCH`** 로
쓴 이유이며, 이 조건은 테스트로 고정돼 있다(`src/lib/i18n/i18n.test.ts`).

## 대체하지 않는 것

이 앱은 다음 **어느 것도 대체하지 않는다.** 이 문장을 약화시키지 않는다.

- 법령이 요구하는 점검·시험운전·기록
- 제조사 취급설명서
- 사업장 안전수칙과 작업허가 절차
- 관리감독자·안전관리자의 판단
- 타음검사 등 사람이 하는 검사

면책 문구(`Disclaimer` 컴포넌트)는 메인과 결과 화면에 **항상** 표시한다.
접거나 숨기지 않는다.

## 왜 이렇게까지 하는가

이 앱이 다루는 것은 **고속으로 회전하는 숫돌**이다. 잘못된 "적합" 한 번이
파손과 비산으로 이어진다. 그리고 그 오판정은 화면에서 보이지 않는다 —
앱은 멀쩡히 돌아가고, 작업자는 확인받았다고 믿는다.

그래서 이 앱은 **틀릴 때 안전한 쪽으로 틀리도록** 만들어져 있다.

- 모르면 통과가 아니라 판정불가
- 신뢰도가 낮으면 사람이 확인해야 풀린다
- 새로 넣는 기능은 **의심을 더할 수는 있어도 덜어낼 수는 없다**

마지막 줄이 기능을 추가할 때의 기준이다. 어떤 기능이 판정을 통과시키는
방향으로만 작동한다면, 그 기능은 이 앱에 넣지 않는다.

## 네 계층

판정은 성격이 다른 네 층으로 나뉜다. **어느 층도 다른 층의 실패나 미확인을
덮을 수 없다.** 하나라도 막히면 진행하지 못한다.

| 계층                  | 누가          | 무엇을                                     |
| --------------------- | ------------- | ------------------------------------------ |
| **GRINDER CONDITION** | 작업자 직접   | 그라인더 장비 상태 5항목                   |
| **WHEEL CONDITION**   | 작업자 직접   | 숫돌 상태 기본 4항목 + 종류별 항목         |
| **SPEC**              | 규칙엔진 14종 | `COMPATIBLE / INCOMPATIBLE / UNDETERMINED` |
| **TRIAL RUN**         | 작업자 직접   | 제122조 ②의 시험운전 — 시간과 이상 여부    |

- 두 Condition을 통과해도 SPEC의 판정불가가 풀리지 않는다.
- SPEC이 적합이어도 Condition에 문제가 있으면 진행할 수 없다.
- 한 Condition을 통과했다고 다른 Condition이 면제되지 않는다.
- 시험운전은 SPEC이 적합인 조합에서만 열린다. 앞 층을 건너뛰지 못한다.
- AI는 어느 층에서도 작업자 응답을 대신 만들 수 없다. AI가 주는 것은 라벨의
  규격 값과 외관 **의심** 정보뿐이며, 최종 안전승인은 어느 층에도 없다.

흐름은 이 순서다.

```
작업 목적 → 명판 확인 → GRINDER CONDITION → 숫돌 확인 → WHEEL CONDITION
          → SPEC(14종) → 작업 전 체크리스트 → TRIAL RUN → 저장
```

## 경고와 차단

규칙엔진 14종 중 셋은 경고(`advisory`)만 한다. **경고는 통과가 아니다.**
전체 판정을 움직이지 않을 뿐, 어느 것도 적합의 근거로 쓰지 않는다.

**덮개 조건**은 입력에 따라 다르다. 작업자가 덮개 없음을 고르거나 덮개 크기를
숫돌 지름보다 작게 넣으면 **판정불가로 막는다.** 덮개 입력이 어긋나지 않으면
경고(직접 확인)로만 남고, 아무것도 넣지 않았거나 모름이면 항목이 생기지 않는다.
덮개가 있다는 입력을 통과의 근거로 쓰지 않는다 — 덮개 장착은 Grinder Condition
Gate가 사람에게 받는다.

| 경고 규칙       | 오해하기 쉬운 점                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 외관 손상       | 한 방향으로만 움직인다. 손상이 **의심**되면 경고를 더하고, 보이지 않으면 아무것도 보장하지 않는다. 「손상 없음」으로 표시하지 않는다 |
| 용도 확인       | 이 항목은 경고뿐이지만, 용도를 못 읽은 경우를 **작업 목적 일치**가 판정불가로 막는다. 작업을 고르지 않은 점검도 판정불가다           |
| 장착 규격(내경) | 명판에 대조할 값이 없어 판정에 쓰지 않는다. 읽은 값을 보여주고 직접 확인하게 한다                                                    |

**숫돌 종류는 경고가 아니라 차단이다.** 작업자가 실물을 보고 부속품 Profile이 있는 종류
(`src/lib/rules/profiles.ts`)를 고른 경우에만 통과한다. Profile이 없는 **기타**와 세부 형식을
고르지 않은 **다이아몬드·컵휠**은 판정불가로 막는다 — 나쁜 숫돌이라는 뜻(부적합)이 아니라
이 앱이 판정할 수 없다는 뜻이다. **모르겠음**으로 둔 경우도 종류가 확인되지 않았으므로 판정불가다.

결합숫돌이 아닌 Profile(플랩·다이아몬드·브러시·샌딩·부직포·연마 패드)은 회전속도·지름만
공통 규칙으로 대조한다. 저장소에 확인된 근거(제122조·oSa)는 결합숫돌에 대한 것이라, 이
종류들의 작업·재료·건습식·회전방향·덮개·유효기한·시험운전은 **근거 미확인**으로 두고 직접
확인 항목으로만 보인다. 통과의 근거로 쓰지 않는다.

**이 Profile들은 회전속도·지름이 맞아도 적합(COMPATIBLE)에 이르지 못한다.**
`AccessoryProfile.scope`가 `'limited'`이기 때문이다 — 작업·덮개·재료 같은 핵심 조건의
근거가 없는 종류를 "검증된 종류"와 같은 결론(적합)으로 끝내면 두 경우를 화면에서 구분할
수 없다. `checkProfileScope()`(engine.ts)가 회전속도·지름 위반이 없어도 판정불가로
막고, 「제한적 규격 대조」 항목에 "RPM과 지름만 대조했습니다. 작업·덮개·장착 적합성은
확인되지 않아 적합 판정을 제공하지 않습니다."를 적는다. 회전속도·지름 위반이 있으면
그대로 부적합이다 — decideVerdict가 부적합을 판정불가보다 먼저 본다.
`scope: 'full'`은 bonded_abrasive와 결합숫돌 세부 형식(Type 1/41·27/28·27/42·6/11)뿐이다.

종류별 상태(세그먼트·날개·와이어·백킹패드
등)는 Wheel Condition Gate에서 작업자가 직접 답한다. AI가 사진으로 본 종류는 제안값일 뿐이고,
작업자의 선택과 다르면 차이를 숨기지 않고 직접 확인을 받는다.

규칙별 조건은 README의 「판정 규칙」에 있다.

## 연구 도구는 현장 배포판에 없다

CSV 내보내기·정답 파일·평가 지표는 검증과 연구에 쓰는 도구다. 작업자 화면에 섞이면
무엇이 점검이고 무엇이 실험인지 흐려진다.

- `NEXT_PUBLIC_ENABLE_RESEARCH_TOOLS=true`로 빌드했을 때만 이력 화면에 생긴다.
  설정이 없거나 정확히 `true`가 아니면 **그리지 않는다.** CSS로 숨기지 않는다.
- 켜진 빌드에서는 패널 맨 위에 「검증/연구용 기능이며 현장 판정을 변경하지 않습니다.」를
  항상 띄운다.
- 연구 도구는 네 계층 어디에도 들어가지 않는다. 저장된 기록을 내보내고 계산할 뿐,
  판정·상태 확인·시험운전·저장 조건을 바꾸지 않는다. 테스트로 고정돼 있다
  (`src/app/history/page.test.tsx`, `src/app/result/page.test.tsx`).
- 연구 도구로 낸 수치를 말할 때도 아래 「연구 결과를 말할 때」를 따른다.

## Grinder Condition Gate

명판 값을 확인한 뒤, 숫돌을 찍기 전에 작업자가 그라인더 전체를 직접 본다.

1. 전원선·플러그 손상
2. 본체 균열·파손
3. 방호덮개 장착·고정
4. 보조손잡이 장착·고정
5. 스핀들·플랜지·고정너트 손상

전부 `확인함`이어야 숫돌 촬영으로 넘어가고, 하나라도 `문제 있음`이면 장비
사용을 중지한다. 미확인도 통과시키지 않는다.

**이 Gate에는 AI 입력이 아예 없다.** 현재 촬영은 명판 중심이라 사진으로는
전원선·덮개·손잡이·스핀들을 볼 수 없다. 보이지 않는 것을 "이상 없음"으로
넘기지 않으려면 추측 대신 사람에게 묻는 것이 맞다. 화면에는 이 경계를 항상
적어 둔다 — _"AI는 명판의 규격 정보만 읽습니다. 그라인더 상태와 작업 안전은
작업자가 직접 확인해야 합니다."_

장비 전체를 찍는 설계가 생기기 전에는 AI 의심 경고도 붙이지 않는다.

## Wheel Condition Gate

숫돌 라벨을 확인한 뒤, 규격 대조 전에 작업자가 실제 숫돌을 직접 점검한다.
네 상태 항목은 서로 대신하지 않는다. 사용기한은 별도의 직접 확인 항목이다.

1. 깨짐·갈라짐·잔금·모서리 파손
2. 휨·변형
3. 중심구멍·장착부 손상
4. 라벨·핵심 규격 식별 가능 여부

각 항목은 작업자가 `확인함` 또는 `문제 있음`으로 직접 답한다. 전부
`확인함`이어야 규격 대조로 진행하며, 하나라도 `문제 있음`이면 숫돌 사용을
중지한다. 미확인 항목도 통과시키지 않는다.

### 사용기한 직접 확인 (2026-10-03)

사용기한 날짜는 규격 입력 필수칸에서 뺐다. 작업자가 `표시 있음`(날짜 입력),
`표시를 찾지 못함`, `표시가 있지만 읽기 어려움`으로 답한다. AI는 이 응답을
채우지 않는다. 후자의 두 응답은 `expiryReview`로 남고, `expiryValid: true`로
바꾸지 않는다. 날짜와 응답이 모두 없으면 기존처럼 판정불가다.

미표기·판독 곤란을 명시하면 사용기한 검사는 `passed: null, advisory: true`로
직접 확인 목록에 남는다. 다른 필수 규칙이 모두 충족되면 규격 판정은 적합이지만
결과·이력·내보낸 문서의 판정 제목은 **적합**으로 표시한다. 사용기한 미확인은
제목에 붙이지 않고 **직접 확인할 항목**과 검사 사유에 남긴다.
이는 국내 제품의 사용 허가나 사용기한 면제가 아니라 앱의 대조 범위 변경이다.
표시된 만료 날짜는 계속 부적합이며, 미표기 선택으로 기존 날짜를 지우지 않는다.
RPM·지름·용도·신뢰도·limited Profile·오프라인 차단은 변경하지 않는다.
구기록은 재판정하지 않고, 구버전 Gate의 기한 문제 있음(false)도 자동 해제하지 않는다.

`visibleDamage`는 이 Gate를 대신하지 않는다. AI가 `suspected`를 반환하면
직접 확인 경고를 더하지만, `none_visible`이어도 버튼을 자동 선택하거나
"손상 없음"이라고 표시하지 않는다. 라벨 신뢰도 검사는 규칙엔진에 그대로
남으며, 사용기한을 읽지 못한 경우는 위 직접 응답 정책을 따른다.

숫돌 외관을 AI가 따로 살펴보는 단계는 없다. 뒷면·가장자리·중심구멍 사진 세
장을 더 받아 AI가 보던 「다각도 외관 확인」은 2026-10-03에 점검 흐름에서 뺐다.
그 확인은 경고만 더했고 판정을 움직이지 않았으므로 판정 규칙은 그대로다.
외관은 이 Gate에서 작업자가 직접 답하는 것으로만 확인하고, AI가 주는 외관
정보는 라벨 사진 한 장에서 본 `visibleDamage`뿐이다. 그 전에 저장된 기록의
다각도 확인 결과와 사진은 이력·기록 문서·CSV·백업에서 그대로 읽힌다.
그 전 버전에서 하다 만 점검을 이어갈 때는 추가 사진과 AI 결과를 되살리지 않고
그 사실을 화면에 알린다. 다만 그 확인이 **의심**했던 숫돌이면 의심은 버리지
않고 이어간다 — 버전이 바뀌었다고 앱이 올린 경고가 조용히 사라지지 않게 한다.

확인 화면에서 하다 만 입력을 되살릴 때 저장된 AI 판독이 지금 기준에 맞지 않으면
두 경우로 나뉜다. 숫돌 라벨 판독에서 종류·용도·외관 같은 일부 값만 어긋났으면 그
값만 모름으로 두고 나머지는 그대로 쓴다. 숫자·원문·신뢰도가 어긋났으면(명판 판독은
어느 값이든) 판독을 통째로 버리고 그 사실을 화면에 알린다. 어느 쪽이든 그 판독은
기록의 OCR 원본으로 남기지 않는다.

통째로 버린 판독이 외관 손상을 **의심**했던 숫돌이면 의심은 이어간다 — 저장된
값이 의심일 때만이고, 읽지 못한 외관 값을 의심으로 채우지 않는다. 버린 판독의
원본 표시는 이어가지 않는다. 표기 일치 항목을 통과시키는 근거로도 쓰이는 값이라,
숫자조차 믿을 수 없는 판독에서 건지면 의심을 더하는 것이 아니라 통과의 근거를
만들게 된다.

통째로 버린 판독으로 확정한 단계는 **제한 대조**로 남긴다(2026-10-04). 그 점검은
적합이 나오지 않고 시험운전도 열리지 않는다. 확정 시점에 앱이 내놓을 AI 판독이
없고, 확정한 값은 직접 입력과 내용이 같다(OCR 원본 없음·원문 없음) — 저장된 출처
하나만 믿고 온라인 대조로 내보내면 직접 입력으로는 받지 못하는 적합을 작업자의
확인만으로 받는다. 확인 화면은 버렸다는 안내와 함께 이것을 알린다.

푸는 길은 둘이고 되찾는 범위가 다르다. **다시 촬영**하면 새 판독이 원본 표시와
외관 판별까지 그대로 들어오고, 확인 화면에서 그 판독을 값마다 대조한다. **결과
화면의 서버 재분석**은 회전속도·지름이 같음을 확인해 제한 대조를 풀고, 다시 읽은
판독을 기록의 OCR 원본으로 남긴다. 다시 읽은 판독의 외관 의심과 원본 표시는
확정값의 빈 자리로 옮겨져 표기 일치·장착 규격 항목이 만들어진다(아래 「서버 분석
없이 넣은 숫돌의 재분석」). 작업자가 확정한 값은 바뀌지 않는다 — 다시 읽은 판독의
종류·용도·유효기한은 판정에 들어가지 않고 견주지도 않는다. 직접 입력을 재분석으로
푼 점검과 같은 범위다.

저장된 출처(서버 분석)는 로컬 판독이나 직접 입력으로 바꿔 적지 않는다. 확인 화면이
사실과 다른 안내를 띄우게 된다. 일부 값만 모름으로 둔 판독은 낮추지 않는다 —
숫자·원문·신뢰도가 기준에 맞는 판독이 화면에 남아 있다. 판정 규칙은 그대로이고,
규칙엔진에 넘기는 판독 경로만 달라진다. 결과 화면과 기록은 이 점검도 「오프라인
제한 대조」라는 같은 이름과 사유 문장으로 적는다 — 기기가 오프라인이었던 것은
아니며, 기록만으로는 제한된 까닭을 구분할 수 없다.

### 서버 분석 없이 넣은 숫돌의 재분석 (2026-10-04)

숫돌 라벨을 서버 판독의 뒷받침 없이(직접 입력·로컬 OCR·통째로 버린 판독) 확정한
점검은 결과 화면에서 서버로 다시 분석할 수 있다. 이때 AI가 사진을 보는 것은
작업자가 Wheel Condition Gate에 답한 **뒤**다. AI가 올린 외관 의심과 읽어 온 라벨 원본 표시가 판정에서
빠지지 않게 한다 — 빠지면 재분석을 거친 점검이 같은 사진을 처음부터 온라인으로
읽은 점검보다 느슨해진다.

- AI가 손상을 **의심**하면 그 의심은 재분석 결과가 도착하는 대로 규격 값에
  더한다. 값이 달라 전환이 막히거나 작업자가 취소해 AI 값을 버려도 의심은 버리지
  않는다. 의심하지 않았으면 아무것도 바꾸지 않는다 — 이미 올라와 있던 의심을
  지우지 않고, "보이지 않음"으로 덮어쓰지도 않는다. 응답을 기다리는 사이 숫돌을
  다시 찍었으면 그 결과는 새 숫돌에 쓰지 않는다 — AI가 본 사진의 숫돌이 아니다.
- 의심이 올라온 숫돌을 **온라인 대조로 바꾸려면** 1번 항목(깨짐·갈라짐)을 다시
  받는다. 앞서 한 답은 그 경고를 보기 전의 것이다. `문제 있음`이면 그 답을
  Gate에 남기고 결과 화면을 닫아 사용 중지를 알린다. AI는 이 답을 대신 만들지
  않는다. 전환하지 않는 경우(값이 다르거나 취소)에는 다시 받지 않는다 — 그
  점검은 판정불가로 남고 시험운전이 열리지 않는다.
- 전환을 받아들이면 AI가 읽은 라벨 원본 표시(rpm·m/s 표기, 내경, 유효기한
  원문)로 **빈 자리만** 채운다. 이미 있는 표기(로컬 OCR이 읽은 것)는 덮지 않는다
  — 덮으면 그 표기가 올렸던 불일치가 사라질 수 있다. 채운 표시는 표기 일치·장착
  규격 항목을 새로 만들 수만 있다. 표기 일치의 통과는 전체 판정을 올리지 못하고,
  어긋나면 판정불가로 막는다. 위에서 버린 판독의 표시를 건지는 것이 아니다 —
  새로 읽어 회전속도·지름이 작업자 입력과 같음을 확인하고 받아들인 판독의 표시이고,
  처음부터 온라인으로 읽은 판독과 같은 자격으로 쓴다.
- 작업자가 확인 화면에서 확정한 값(회전속도·지름·두께·용도·종류·유효기한)은
  AI 값으로 바꾸지 않는다.

남는 한계. 고치려면 따로 정해야 한다.

- 로컬 OCR이 이미 읽어 둔 표기를 서버가 **다르게** 읽어도 로컬 표기가 그대로
  쓰인다. 서버가 읽은 쪽이 어긋나는 표기였다면, 처음부터 온라인으로 읽었을 때
  막혔을 점검이 재분석을 거쳐 통과할 수 있다. 직접 입력한 숫돌에는 이 한계가 없다.
- 재분석이 견주는 값은 회전속도와 지름뿐이다. 용도·유효기한·종류가 AI가 읽은
  것과 달라도 알리지 않는다.
- 받아들이지 않은 재분석이 올린 의심은 규격 값에 남지만, 그 판독(OCR 원본)은
  기록에 남지 않는다. 다시 받은 1번 항목의 답도 기록에는 따로 남지 않는다.
- `문제 있음`으로 답한 뒤 숫돌을 다시 찍으면 새 사진의 판독과 답으로 처음부터
  다시 한다. 앞선 의심과 답은 이어지지 않는다(재촬영의 기존 규칙과 같다).

계층 관계는 위 「네 계층」에 한 번만 적는다.

## 시험운전 (제122조 ②)

규격이 맞고 두 Gate와 체크리스트가 모두 끝난 뒤에만 시작할 수 있다.
부적합·판정불가 조합의 시험운전을 앱이 유도하면 그 자체가 사고 경로다.

작업 시작 전 1분 이상, 숫돌 교체 후 3분 이상. 남은 시간은 **절대 종료시각**
에서 계산한다 — 틱을 세면 화면이 멈춘 만큼 시간이 짧아져, 앱이 법이 정한
시간을 마음대로 줄이는 셈이 된다.

타이머가 끝나면 작업자가 다섯 가지(진동·소음·흔들림·파손 징후·장비 이상)를
직접 답한다. AI는 어느 것도 판별하지 못하고 대신 고르지도 않는다. 이상이
확인되면 작업 중지 안내를 띄우고 저장 문구가 「중지 결과 저장」으로 바뀐다.
문제가 확인된 결과를 「점검 완료」라고 부르지 않는다.

**이 앱은 시간을 재고 답을 남길 뿐이다.** 법정 절차를 대신한다거나 시간을
줄여준다고 말하지 않는다.

## 최종 체크리스트에 남는 것

방호덮개·보조손잡이는 Grinder Condition Gate로, 숫돌 손상은 Wheel Condition
Gate로 옮겼다. **같은 것을 두 번 묻지 않는다** — 두 번째는 읽지 않고 누르게
되고, 그 순간 체크는 확인이 아니라 절차가 된다.

최종 체크리스트에는 보호구 착용, 작업물 고정, 주변 사람·가연물 확인이 남는다.
기계도 숫돌도 아닌 **사람과 작업 환경**이라 어느 Gate에도 속하지 않는다.
불꽃 방향은 매 순간 달라지는 항목이라 체크박스로 만들지 않고 작업 직전
안내로 둔다.

과거 기록을 읽을 수 있도록 `SafetyChecklist` 필드와 CSV 열은 지우지 않는다.
화면에서 빼는 것과 저장 구조에서 지우는 것은 다르다.

## 연구 결과를 말할 때

발표·논문에서도 같은 경계를 지킨다.

- 규칙엔진 테스트 개수와 **실물 촬영 세트 수**를 섞어 말하지 않는다.
  전자는 합성 값 로직 검증, 후자는 실험이다.
- "판정 오류"와 "인식 오류"를 나눠 보고한다. 판정이 결정론적 규칙이므로
  **부적합 탐지 재현율 = 필드 추출 정확도**다.
- 직접 확인한 것만 확인했다고 말한다. 실기기 카메라, 배포, 실제 인식률은
  각각 따로 확인해야 한다.

측정 방법은 [validation-plan.md](validation-plan.md)에, 실물 검증 절차는
[rc-field-validation.md](rc-field-validation.md)에 있다.
