# 안전 경계 — 이 앱이 하지 않는 것

앱이 **무엇을 하는가**보다 **무엇을 하지 않는가**를 먼저 정한다.
경계가 흐려지면 작업자가 다른 확인 절차를 생략하게 된다.

이 문서는 화면 문구·문서·발표 자료 전체에 적용된다.
코드 규칙은 `.claude/rules/safety-critical.md`에 있다.

---

## 한 문장으로

> 이 앱은 **라벨에 표시된 규격끼리 서로 맞는지**만 대조한다.
> 작업이 안전한지는 말하지 않는다.

---

## 하는 것 / 하지 않는 것

| 한다                                                   | 하지 않는다                               |
| ------------------------------------------------------ | ----------------------------------------- |
| 라벨에 적힌 값을 읽는다                                | 값을 추정하거나 채워 넣는다               |
| 읽은 값끼리 규칙으로 대조한다                          | "안전하다"고 승인한다                     |
| 못 읽으면 판정불가라고 말한다                          | 모르는 것을 통과로 처리한다               |
| 부적합일 때 다음 행동을 알려준다                       | 제품을 추천한다                           |
| 사진으로 숫돌 **종류**를 제안하고 작업자가 고르게 한다 | 사진으로 균열 **없음**을 판정한다         |
| 사진에서 손상이 **의심**되면 경고한다                  | 손상이 안 보인다고 「손상 없음」이라 한다 |
| 명판에 적힌 최대 지름을 읽는다                         | 사진에서 치수를 **측정**한다              |
| 체크리스트 항목을 보여준다                             | 체크리스트를 대신 체크한다                |

## 절대 쓰지 않는 표현

화면·문서·발표 어디에도 쓰지 않는다.

- ❌ 안전합니다 / 사용해도 됩니다 / 안전 확인 완료 / 검사 통과
- ❌ 이 숫돌을 쓰세요 (제품 추천)
- ❌ 균열이 없습니다
- ✅ 표시된 규격끼리는 서로 맞습니다
- ✅ 값이 부족해 판정할 수 없습니다
- ✅ 사진으로는 미세균열을 확인할 수 없습니다. 장착 전 타음검사를 하세요

번역에도 그대로 적용된다. 영어 판정을 `OK to use`가 아니라 **`SPECS MATCH`** 로
쓴 이유이며, 이 조건은 테스트로 고정돼 있다(`src/lib/i18n/i18n.test.ts`).

## 대체하지 않는 것

이 앱은 다음 **어느 것도 대체하지 않는다.** 이 문장을 약화시키지 않는다.

- 법령이 요구하는 점검·시험운전·기록
- 제조사 취급설명서
- 사업장 안전수칙과 작업허가 절차
- 관리감독자·안전관리자의 판단
- 타음검사 등 사람이 하는 검사

면책 문구(`Disclaimer` 컴포넌트)는 메인과 결과 화면에 **항상** 표시한다.
접거나 숨기지 않는다.

## 왜 이렇게까지 하는가

이 앱이 다루는 것은 **고속으로 회전하는 숫돌**이다. 잘못된 "적합" 한 번이
파손과 비산으로 이어진다. 그리고 그 오판정은 화면에서 보이지 않는다 —
앱은 멀쩡히 돌아가고, 작업자는 확인받았다고 믿는다.

그래서 이 앱은 **틀릴 때 안전한 쪽으로 틀리도록** 만들어져 있다.

- 모르면 통과가 아니라 판정불가
- 신뢰도가 낮으면 사람이 확인해야 풀린다
- 새로 넣는 기능은 **의심을 더할 수는 있어도 덜어낼 수는 없다**

마지막 줄이 기능을 추가할 때의 기준이다. 어떤 기능이 판정을 통과시키는
방향으로만 작동한다면, 그 기능은 이 앱에 넣지 않는다.

## 네 계층

판정은 성격이 다른 네 층으로 나뉜다. **어느 층도 다른 층의 실패나 미확인을
덮을 수 없다.** 하나라도 막히면 진행하지 못한다.

| 계층                  | 누가          | 무엇을                                     |
| --------------------- | ------------- | ------------------------------------------ |
| **GRINDER CONDITION** | 작업자 직접   | 그라인더 장비 상태 5항목                   |
| **WHEEL CONDITION**   | 작업자 직접   | 숫돌 상태 기본 4항목 + 종류별 항목         |
| **SPEC**              | 규칙엔진 14종 | `COMPATIBLE / INCOMPATIBLE / UNDETERMINED` |
| **TRIAL RUN**         | 작업자 직접   | 제122조 ②의 시험운전 — 시간과 이상 여부    |

- 두 Condition을 통과해도 SPEC의 판정불가가 풀리지 않는다.
- SPEC이 적합이어도 Condition에 문제가 있으면 진행할 수 없다.
- 한 Condition을 통과했다고 다른 Condition이 면제되지 않는다.
- 시험운전은 SPEC이 적합인 조합에서만 열린다. 앞 층을 건너뛰지 못한다.
- AI는 어느 층에서도 작업자 응답을 대신 만들 수 없다. AI가 주는 것은 라벨의
  규격 값과 외관 **의심** 정보뿐이며, 최종 안전승인은 어느 층에도 없다.

흐름은 이 순서다.

```
작업 목적 → 명판 확인 → GRINDER CONDITION → 숫돌 확인 → WHEEL CONDITION
          → SPEC(14종) → 작업 전 체크리스트 → TRIAL RUN → 저장
```

## 경고와 차단

규칙엔진 14종 중 셋은 경고(`advisory`)만 한다. **경고는 통과가 아니다.**
전체 판정을 움직이지 않을 뿐, 어느 것도 적합의 근거로 쓰지 않는다.

**덮개 조건**은 입력에 따라 다르다. 작업자가 덮개 없음을 고르거나 덮개 크기를
숫돌 지름보다 작게 넣으면 **판정불가로 막는다.** 덮개 입력이 어긋나지 않으면
경고(직접 확인)로만 남고, 아무것도 넣지 않았거나 모름이면 항목이 생기지 않는다.
덮개가 있다는 입력을 통과의 근거로 쓰지 않는다 — 덮개 장착은 Grinder Condition
Gate가 사람에게 받는다.

| 경고 규칙       | 오해하기 쉬운 점                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 외관 손상       | 한 방향으로만 움직인다. 손상이 **의심**되면 경고를 더하고, 보이지 않으면 아무것도 보장하지 않는다. 「손상 없음」으로 표시하지 않는다 |
| 용도 확인       | 이 항목은 경고뿐이지만, 용도를 못 읽은 경우를 **작업 목적 일치**가 판정불가로 막는다. 작업을 고르지 않은 점검도 판정불가다           |
| 장착 규격(내경) | 명판에 대조할 값이 없어 판정에 쓰지 않는다. 읽은 값을 보여주고 직접 확인하게 한다                                                    |

**숫돌 종류는 경고가 아니라 차단이다.** 작업자가 실물을 보고 부속품 Profile이 있는 종류
(`src/lib/rules/profiles.ts`)를 고른 경우에만 통과한다. Profile이 없는 **기타**와 세부 형식을
고르지 않은 **다이아몬드·컵휠**은 판정불가로 막는다 — 나쁜 숫돌이라는 뜻(부적합)이 아니라
이 앱이 판정할 수 없다는 뜻이다. **모르겠음**으로 둔 경우도 종류가 확인되지 않았으므로 판정불가다.

결합숫돌이 아닌 Profile(플랩·다이아몬드·브러시·샌딩·부직포·연마 패드)은 회전속도·지름만
공통 규칙으로 대조한다. 저장소에 확인된 근거(제122조·oSa)는 결합숫돌에 대한 것이라, 이
종류들의 작업·재료·건습식·회전방향·덮개·유효기한·시험운전은 **근거 미확인**으로 두고 직접
확인 항목으로만 보인다. 통과의 근거로 쓰지 않는다.

**이 Profile들은 회전속도·지름이 맞아도 적합(COMPATIBLE)에 이르지 못한다.**
`AccessoryProfile.scope`가 `'limited'`이기 때문이다 — 작업·덮개·재료 같은 핵심 조건의
근거가 없는 종류를 "검증된 종류"와 같은 결론(적합)으로 끝내면 두 경우를 화면에서 구분할
수 없다. `checkProfileScope()`(engine.ts)가 회전속도·지름 위반이 없어도 판정불가로
막고, 「제한적 규격 대조」 항목에 "RPM과 지름만 대조했습니다. 작업·덮개·장착 적합성은
확인되지 않아 적합 판정을 제공하지 않습니다."를 적는다. 회전속도·지름 위반이 있으면
그대로 부적합이다 — decideVerdict가 부적합을 판정불가보다 먼저 본다.
`scope: 'full'`은 bonded_abrasive와 결합숫돌 세부 형식(Type 1/41·27/28·27/42·6/11)뿐이다.

종류별 상태(세그먼트·날개·와이어·백킹패드
등)는 Wheel Condition Gate에서 작업자가 직접 답한다. AI가 사진으로 본 종류는 제안값일 뿐이고,
작업자의 선택과 다르면 차이를 숨기지 않고 직접 확인을 받는다.

규칙별 조건은 README의 「판정 규칙」에 있다.

## 연구 도구는 현장 배포판에 없다

CSV 내보내기·정답 파일·평가 지표는 검증과 연구에 쓰는 도구다. 작업자 화면에 섞이면
무엇이 점검이고 무엇이 실험인지 흐려진다.

- `NEXT_PUBLIC_ENABLE_RESEARCH_TOOLS=true`로 빌드했을 때만 이력 화면에 생긴다.
  설정이 없거나 정확히 `true`가 아니면 **그리지 않는다.** CSS로 숨기지 않는다.
- 켜진 빌드에서는 패널 맨 위에 「검증/연구용 기능이며 현장 판정을 변경하지 않습니다.」를
  항상 띄운다.
- 연구 도구는 네 계층 어디에도 들어가지 않는다. 저장된 기록을 내보내고 계산할 뿐,
  판정·상태 확인·시험운전·저장 조건을 바꾸지 않는다. 테스트로 고정돼 있다
  (`src/app/history/page.test.tsx`, `src/app/result/page.test.tsx`).
- 연구 도구로 낸 수치를 말할 때도 아래 「연구 결과를 말할 때」를 따른다.

## Grinder Condition Gate

명판 값을 확인한 뒤, 숫돌을 찍기 전에 작업자가 그라인더 전체를 직접 본다.

1. 전원선·플러그 손상
2. 본체 균열·파손
3. 방호덮개 장착·고정
4. 보조손잡이 장착·고정
5. 스핀들·플랜지·고정너트 손상

전부 `확인함`이어야 숫돌 촬영으로 넘어가고, 하나라도 `문제 있음`이면 장비
사용을 중지한다. 미확인도 통과시키지 않는다.

**이 Gate에는 AI 입력이 아예 없다.** 현재 촬영은 명판 중심이라 사진으로는
전원선·덮개·손잡이·스핀들을 볼 수 없다. 보이지 않는 것을 "이상 없음"으로
넘기지 않으려면 추측 대신 사람에게 묻는 것이 맞다. 화면에는 이 경계를 항상
적어 둔다 — _"AI는 명판의 규격 정보만 읽습니다. 그라인더 상태와 작업 안전은
작업자가 직접 확인해야 합니다."_

장비 전체를 찍는 설계가 생기기 전에는 AI 의심 경고도 붙이지 않는다.

## Wheel Condition Gate

숫돌 라벨을 확인한 뒤, 규격 대조 전에 작업자가 실제 숫돌을 직접 점검한다.
네 상태 항목은 서로 대신하지 않는다. 사용기한은 별도의 직접 확인 항목이다.

1. 깨짐·갈라짐·잔금·모서리 파손
2. 휨·변형
3. 중심구멍·장착부 손상
4. 라벨·핵심 규격 식별 가능 여부

각 항목은 작업자가 `확인함` 또는 `문제 있음`으로 직접 답한다. 전부
`확인함`이어야 규격 대조로 진행하며, 하나라도 `문제 있음`이면 숫돌 사용을
중지한다. 미확인 항목도 통과시키지 않는다.

### 사용기한 직접 확인 (2026-10-03)

사용기한 날짜는 규격 입력 필수칸에서 뺐다. 작업자가 `표시 있음`(날짜 입력),
`표시를 찾지 못함`, `표시가 있지만 읽기 어려움`으로 답한다. AI는 이 응답을
채우지 않는다. 후자의 두 응답은 `expiryReview`로 남고, `expiryValid: true`로
바꾸지 않는다. 날짜와 응답이 모두 없으면 기존처럼 판정불가다.

미표기·판독 곤란을 명시하면 사용기한 검사는 `passed: null, advisory: true`로
직접 확인 목록에 남는다. 다른 필수 규칙이 모두 충족되면 규격 판정은 적합이지만
결과·이력·내보낸 문서의 판정 제목은 **적합**으로 표시한다. 사용기한 미확인은
제목에 붙이지 않고 **직접 확인할 항목**과 검사 사유에 남긴다.
이는 국내 제품의 사용 허가나 사용기한 면제가 아니라 앱의 대조 범위 변경이다.
표시된 만료 날짜는 계속 부적합이며, 미표기 선택으로 기존 날짜를 지우지 않는다.
RPM·지름·용도·신뢰도·limited Profile·제한 대조 차단은 변경하지 않는다.
구기록은 재판정하지 않고, 구버전 Gate의 기한 문제 있음(false)도 자동 해제하지 않는다.

`visibleDamage`는 이 Gate를 대신하지 않는다. AI가 `suspected`를 반환하면
직접 확인 경고를 더하지만, `none_visible`이어도 버튼을 자동 선택하거나
"손상 없음"이라고 표시하지 않는다. 라벨 신뢰도 검사는 규칙엔진에 그대로
남으며, 사용기한을 읽지 못한 경우는 위 직접 응답 정책을 따른다.

숫돌 외관을 AI가 따로 살펴보는 단계는 없다. 뒷면·가장자리·중심구멍 사진 세
장을 더 받아 AI가 보던 「다각도 외관 확인」은 2026-10-03에 점검 흐름에서 뺐다.
그 확인은 경고만 더했고 판정을 움직이지 않았으므로 판정 규칙은 그대로다.
외관은 이 Gate에서 작업자가 직접 답하는 것으로만 확인하고, AI가 주는 외관
정보는 라벨 사진 한 장에서 본 `visibleDamage`뿐이다. 그 전에 저장된 기록의
다각도 확인 결과와 사진은 이력·기록 문서·CSV·백업에서 그대로 읽힌다.
그 전 버전에서 하다 만 점검을 이어갈 때는 추가 사진과 AI 결과를 되살리지 않고
그 사실을 화면에 알린다. 다만 그 확인이 **의심**했던 숫돌이면 의심은 버리지
않고 이어간다 — 버전이 바뀌었다고 앱이 올린 경고가 조용히 사라지지 않게 한다.

확인 화면에서 하다 만 입력을 되살릴 때 저장된 AI 판독이 지금 기준에 맞지 않으면
두 경우로 나뉜다. 숫돌 라벨 판독에서 종류·용도·외관 같은 일부 값만 어긋났으면 그
값만 모름으로 두고 나머지는 그대로 쓴다. 숫자·원문·신뢰도가 어긋났으면(명판 판독은
어느 값이든) 판독을 통째로 버리고 그 사실을 화면에 알린다. 어느 쪽이든 그 판독은
기록의 OCR 원본으로 남기지 않는다.

통째로 버린 판독이 외관 손상을 **의심**했던 숫돌이면 의심은 이어간다 — 저장된
값이 의심일 때만이고, 읽지 못한 외관 값을 의심으로 채우지 않는다. 버린 판독의
원본 표시는 이어가지 않는다. 표기 일치 항목을 통과시키는 근거로도 쓰이는 값이라,
숫자조차 믿을 수 없는 판독에서 건지면 의심을 더하는 것이 아니라 통과의 근거를
만들게 된다.

통째로 버린 판독으로 확정한 단계는 **제한 대조**로 남긴다(2026-10-04). 그 점검은
적합이 나오지 않고 시험운전도 열리지 않는다. 확정 시점에 앱이 내놓을 AI 판독이
없고, 확정한 값은 직접 입력과 내용이 같다(OCR 원본 없음·원문 없음) — 저장된 출처
하나만 믿고 제한 없이 내보내면 직접 입력으로는 받지 못하는 적합을 작업자의
확인만으로 받는다. 확인 화면은 버렸다는 안내와 함께 이것을 알린다.

푸는 길은 둘이고 되찾는 범위가 다르다. **다시 촬영**하면 새 판독이 원본 표시와
외관 판별까지 그대로 들어오고, 확인 화면에서 그 판독을 값마다 대조한다. **결과
화면의 서버 재분석**은 다시 읽은 판독이 확정값과 어긋나지 않음을 확인해(회전속도·
지름은 같아야 하고, 용도·유효기한·종류는 달라서는 안 되며, 낮은 신뢰도로 읽은
판독은 받지 않는다) 제한 대조를 풀고, 다시 읽은 판독을 기록에 재분석 판독으로
남긴다(OCR 원본 자리가 아니다 — 아래 소절의 「재분석 판독의 기록」). 다시 읽은
판독의 외관 의심과 원본 표시는 확정값의 빈 자리로 옮겨져 표기 일치·장착 규격 항목이
만들어진다(아래 「서버 분석 없이 넣은 숫돌의 재분석」). 작업자가 확정한 값은 바뀌지
않는다 — 다시 읽은 판독의 종류·용도·유효기한은 판정에 들어가지 않는다. 확정값과
다르면 제한 대조를 풀지 않을 뿐이다. 직접 입력을 재분석으로 푼 점검과 같은 범위다.

저장된 출처(서버 분석)는 로컬 판독이나 직접 입력으로 바꿔 적지 않는다. 확인 화면이
사실과 다른 안내를 띄우게 된다. 일부 값만 모름으로 둔 판독은 낮추지 않는다 —
숫자·원문·신뢰도가 기준에 맞는 판독이 화면에 남아 있다. 판정 규칙은 그대로이고,
규칙엔진에 넘기는 판독 경로만 달라진다. 결과 화면과 기록이 이 점검을 어떻게
적는지는 바로 아래에 있다.

### 제한 대조의 이름과 까닭 (2026-10-04)

확정한 값을 뒷받침하는 서버 판독이 확인되지 않은 점검을 **제한 대조**라고 부른다.
위반이 없어도 적합이 나오지 않고 시험운전도 열리지 않는다. 그렇게 되는 경우는 넷이다.

| 까닭        | 기록 값       | 무슨 일이 있었나                                                    |
| ----------- | ------------- | ------------------------------------------------------------------- |
| 직접 입력   | `manual`      | 서버에 닿지 못해 작업자가 명판·라벨을 보고 직접 입력했다            |
| 기기 안 OCR | `local_ocr`   | 기기 안 OCR 엔진이 읽은 것이 확인됐다                               |
| 버린 판독   | `dropped_ocr` | 확인 화면에 저장된 서버 판독을 읽을 수 없어 통째로 버린 채 확정했다 |
| 기록 없음   | `unknown`     | 까닭을 적을 수 없다 — 아래 「모르면 적지 않는다」의 경우들          |

직접 입력 말고는 기기가 오프라인이었다고 말할 수 없고, 버린 판독은 서버 분석까지
거쳤다. 그래서
까닭을 가리지 않고 뜨는 문구 — 결과 화면의 제목·검사 항목·안내, 내보낸 문서,
규칙엔진이 기록에 남기는 이름과 사유 — 는 까닭 하나를 단정하지 않는다. 단정하면
나머지 경우에 거짓이 된다. 그 문구들에서는 이렇게 쓴다.

- ❌ 오프라인 제한 대조 / 서버 분석 없이 / 서버에 닿지 못해 / 작업자가 입력한 값으로만
- ❌ 연결되면 / 연결이 돌아왔습니다 / 온라인 대조로 전환 / 오프라인 결과
- ✅ 제한 대조 / 확정한 값을 뒷받침하는 서버 판독이 확인되지 않아 / 제한 대조 풀기

이 조건은 테스트로 고정돼 있다(`src/lib/i18n/i18n.test.ts`의 「제한 대조 문구」).
까닭을 아는 자리는 사실대로 말한다 — 확인 화면의 배지(서버로 분석하지 못했다, 이
기기에서 읽었다, 저장된 판독을 읽을 수 없다), 재분석 패널의 연결 상태(지금 기기가
오프라인이다), 그리고 기록된 까닭을 적는 줄(아래)이 그렇다.

까닭은 확인 화면이 확정할 때 단계(명판·숫돌 라벨)별로 하나씩 남긴다. 둘이 겹치면
출처가 먼저다(직접 입력 → 기기 안 OCR → 버린 판독) — 기기 안 OCR로 읽은 판독이
버려진 점검은 `local_ocr`다. 결과 화면과 내보낸 문서는 남은 까닭을 「그라인더:
서버에 닿지 못해 직접 입력한 값입니다.」처럼 한 줄씩 그대로 적고, 기록·CSV·백업에도
남는다. **추정해 채우지 않는다.** 남아 있지 않으면 「제한된 까닭이 기록되지
않았습니다.」라고 적는다. 확정한 값만으로는 직접 입력과 버린 판독이 구분되지 않는다
(둘 다 OCR 원본이 없다).

**모르면 적지 않는다.** 확인 화면은 서버 판독이 아닐 수 있는 값을 넓게 잡아
제한한다 — 기기 안 OCR이 읽은 값뿐 아니라, 읽을 때 기기가 오프라인으로 보고됐을
뿐인 값과 출처가 남지 않은 확인 화면 입력도 함께 제한한다. 뒤의 둘은 서버가 읽은
값일 수 있으므로 `local_ocr`로 적지 않고 `unknown`으로 둔다. 그 값의 판독을 버린
경우도 `dropped_ocr`로 적지 않는다(서버 판독이었는지 모른다). 까닭을 적기 전 형식의
진행 중 점검과, 판독 경로 표시를 읽지 못해 엄격한 쪽으로 본 점검도 `unknown`이다.
제한 범위는 그대로 넓고, 기록에 단정하는 범위만 좁다.

**까닭은 판정에 쓰지 않는다.** 까닭이 무엇이든 제한 대조는 적합을 내지 않고, 까닭을
근거로 제한을 풀지 않는다. 제한 여부와 까닭은 따로 넘기고 따로 읽는다 — 까닭이
없거나 어긋나도 제한은 그대로다. 푸는 길은 까닭과 무관하게 서버 재분석과 다시 촬영
둘뿐이라 안내는 까닭별로 나누지 않는다.

**풀린 단계의 까닭은 남기지 않는다.** 까닭 칸은 저장하는 순간에 제한돼 있는 단계만
적는다. 결과 화면의 서버 재분석을 받아들여 제한이 풀린 단계는 까닭도 함께 지운다 —
풀린 단계에 까닭이 남으면 제한 여부와 어긋나고, 화면의 까닭 줄이 지금도 제한된
것처럼 읽힌다. 그래서 두 단계가 모두 풀려 저장된 기록(`analysisMode=online`)에서는
처음에 왜 제한됐었는지 알 수 없다. 한 단계만 풀린 기록에는 남은 단계의 까닭만 있다.

2026-10-04 전에는 이름이 「오프라인 제한 대조」였고 사유가 「서버 분석 없이…」였다.
문구만 바꿨고 어떤 점검이 이 항목을 받는지와 판정은 그대로라 규칙 세트 버전은
올리지 않았다. 그 전에 저장된 기록은 옛 이름을 갖고 있지만 화면은 지금 이름으로
읽는다. 그 기록에는 까닭이 없다 — CSV에서는 빈 칸이고, 내보낸 문서에는 기록되지
않았다고만 적힌다. 「제한적 규격 대조」(부속품 종류의 근거가 부족한 경우)와는 다른
규칙이다. 그쪽은 서버 재분석으로 풀리지 않는다.

이어받은 의심은 새 라벨 사진을 찍으면 지운다 — 다른 숫돌일 수 있다. 다만 이
규칙은 작업자가 확인 화면에서 경고를 **본 뒤 스스로** 다시 찍는 경우의 것이다.
앱이 확인 화면을 되살리지 못해 라벨을 다시 찍게 되는 경우가 있다 — 판독값을
대조할 사진을 되살리지 못했거나, 저장된 입력을 통째로 읽지 못했거나, 작업자가
복원보다 먼저 새 사진을 찍었거나, 숫돌 종류를 바꿔 저장된 입력을 치운 직후에
화면이 닫힌 경우다. 그 사진은 작업자가 고른 것이 아니라 앱이 요구한 것이므로,
그때 저장돼 있던 의심은 지우지 않고 이어간다 — Gate에서 알리고, 확정한 규격에도
의심으로 남긴다. 이 경우에도 저장된 값이 의심일 때만이다. 사진이 없다거나 입력을
읽지 못했다는 것을 의심의 근거로 삼지 않는다.

같은 숫돌인지는 앱이 알 수 없다. 그래서 그 의심이 다시 찍기 전에 올라온 것이며
다른 숫돌을 찍었더라도 실물을 직접 확인하라고 확인 화면에 함께 적는다. 다른
숫돌이었다면 그 숫돌에 근거 없는 경고가 붙는다 — 확인 화면의 Gate 경고와, 결과
화면의 직접 확인 항목(외관 손상)이다. 외관 손상은 경고만 하고 판정을 움직이지
않는다. 그 점검이 제한 대조로 끝났다면, 서버 재분석으로 제한 대조를 풀 때 이
의심 때문에 손상 항목을 한 번 더 받는다(아래 「서버 분석 없이 넣은 숫돌의 재분석」).
결과 화면과 기록도 그 의심이 다시 찍기 전의 것임을 함께 밝힌다(바로 아래 「외관
의심의 출처」). 대조할 사진이 없는 확인 화면은 열지 않는다 — 사진은 판독값을 대조할
유일한 독립 근거다.

### 외관 의심의 출처 (2026-10-04)

확정한 규격의 외관 의심은 이 점검의 라벨 사진을 읽은 판독에서만 오지 않는다. 위의
이어받은 의심(이전 버전의 다각도 확인·통째로 버린 판독·다시 찍기 전의 draft)과 결과
화면의 서버 재분석도 규격을 의심으로 만든다. 그런데 규칙엔진의 사유 문장은 어느
경우든 「사진에서 깨짐·균열로 보이는 부분이 있습니다」이고, 기록에 남는 사진과 OCR
원본은 그 의심을 담고 있지 않을 수 있다. 다시 찍은 사진은 다른 숫돌의 것일 수도
있다. 그래서 의심으로 확정할 때 **어디서 온 의심인지**를 규격에 함께 남긴다
(`WheelSpec.visibleDamageSources`). 여러 곳에서 왔으면 모두 적는다.

| 출처          | 뜻                                                                         |
| ------------- | -------------------------------------------------------------------------- |
| `label_photo` | 이 점검의 라벨 사진을 읽은 판독(확인 화면에서 보던 판독)                   |
| `reanalysis`  | 결과 화면의 서버 재분석. 같은 라벨 사진을 다시 읽은 판독                   |
| `legacy_exam` | 이전 버전의 다각도 외관 확인. 그 사진과 결과는 기록에 없다                 |
| `dropped_ocr` | 읽을 수 없어 통째로 버린 판독. 이 라벨 사진을 읽었지만 기록에 없다         |
| `carried`     | 확인 화면을 되살리지 못해 라벨을 다시 찍기 전의 draft. 다른 숫돌일 수 있다 |

- **의심을 덜어내지 않는다.** 출처는 판정에 쓰지 않고(규칙엔진은 `visibleDamage`만
  본다), 의심을 지우거나 약하게 만드는 데도 쓰지 않는다. 엔진의 사유 문장도 그대로다.
- 결과 화면·이력·기록 문서는 「외관 손상」 항목의 사유 아래에 **이어받은 출처마다**
  한 줄을 붙인다(`legacy_exam`·`dropped_ocr`·`carried`). 이 점검의 라벨 사진을 읽은
  판독(`label_photo`·`reanalysis`)에는 줄이 없다 — 엔진 문장이 그 판독을 그대로
  말한다.
- 이어받은 출처의 줄은 **다른 출처가 더 있어도 빼지 않는다.** 이 사진의 판독도
  의심했다고 빼면, 결과 화면에서 서버 재분석이 의심을 더하는 순간 보이던 줄이
  사라진다. 대신 문장이 달라진다. 출처가 하나뿐일 때만 「이 의심은 …에서 왔다」·
  「이 점검에 쓴 라벨 사진의 판독에서 나온 것이 아니다」라고 말하고, 둘 이상이거나
  지금 목록에 없는 출처(다른 버전이 쓴 기록)가 섞였으면 「…에서도 의심이 있었다」
  고만 말한다.
- 어느 줄이든 **실물을 직접 확인하라**는 말로 끝난다. 「그 판독은 기록에 없다」로
  끝내면 근거가 사라진 경고처럼 읽혀 엔진 문장의 「사용하지 말고」를 무른다. 이전
  버전의 확인과 통째로 버린 판독은 새 사진을 찍으면 지워지는 흔적이라, 그 의심은
  지금 사진의 숫돌에 대한 것이다. 다시 찍기 전에서 이어받은 의심에는 다른 숫돌을
  촬영했더라도 확인하라는 말을 함께 적는다.
- CSV는 `visibleDamageSources` 열에 적는다. `visibleDamage` 열만으로는 이
  사진의 판독이 의심한 것과 이어받은 의심이 같은 `suspected`로 적힌다. 의심이 아닌
  기록은 빈 칸이다.
- 이 표시가 생기기 전의 기록에는 출처가 없다. 없다고 라벨 사진 판독으로 채우지
  않는다 — 출처 미기록으로 읽고, 화면에도 아무것도 덧붙이지 않는다.

남는 한계. 고치려면 따로 정해야 한다.

- 엔진의 사유 문장은 출처와 무관하게 「사진에서 …」다. 다시 찍기 전에서 이어받은
  의심이면 그 문장과 출처 줄이 나란히 놓인다. 문장 자체를 출처에 따라 나누려면
  규칙엔진에 사유 코드를 더해야 한다.
- `label_photo`는 그 판독이 기록의 OCR 원본으로 남았는지를 말하지 않는다. 일부 값만
  모름으로 읽은 판독이 의심한 경우에도 `label_photo`지만, 그 판독은 OCR 원본으로
  남기지 않는다(위 「확인 화면에서 하다 만 입력을 되살릴 때」). 화면에는 줄이 붙지
  않고, 기록에서는 OCR 원본이 있는지로 가려야 한다.
- 서버 재분석만이 올린 의심(`reanalysis` 하나)에는 이 줄이 없다. 그 판독을 기록에
  남기고 화면에 알리는 것은 재분석 쪽에서 다룬다(아래 소절).
- 출처 값은 다른 목록형 값과 같은 기준으로 검사한다. 지금 목록에 없는 출처가 든
  규격은 새로고침 복원·이어하기·백업 가져오기에서 통째로 무효다 — 출처 값을 더한
  버전의 진행 중 점검을 옛 버전이 읽으면 숫돌 단계가 의심과 함께 버려진다.

### 서버 분석 없이 넣은 숫돌의 재분석 (2026-10-04)

숫돌 라벨을 서버 판독의 뒷받침 없이(직접 입력·로컬 OCR·통째로 버린 판독) 확정한
점검은 결과 화면에서 서버로 다시 분석할 수 있다. 이때 AI가 사진을 보는 것은
작업자가 Wheel Condition Gate에 답한 **뒤**다. AI가 올린 외관 의심과 읽어 온 라벨 원본 표시가 판정에서
빠지지 않게 한다 — 빠지면 재분석을 거친 점검이 같은 사진을 처음부터 온라인으로
읽은 점검보다 느슨해진다.

- AI가 손상을 **의심**하면 그 의심은 재분석 결과가 도착하는 대로 규격 값에
  더한다. 값이 달라 전환이 막히거나 작업자가 취소해 AI 값을 판정에 쓰지 않아도
  의심은 버리지 않는다. 의심하지 않았으면 아무것도 바꾸지 않는다 — 이미 올라와 있던 의심을
  지우지 않고, "보이지 않음"으로 덮어쓰지도 않는다. 응답을 기다리는 사이 숫돌을
  다시 찍었으면 그 결과는 새 숫돌에 쓰지 않는다 — AI가 본 사진의 숫돌이 아니다.
- 의심이 올라온 숫돌의 **제한 대조를 풀려면** 1번 항목(깨짐·갈라짐)을 다시
  받는다. 앞서 한 답은 그 경고를 보기 전의 것이다. `문제 있음`이면 그 답을
  Gate에 남기고 결과 화면을 닫아 사용 중지를 알린다. AI는 이 답을 대신 만들지
  않는다. 제한 대조를 풀지 않는 경우(값이나 표기가 다르거나, 낮은 신뢰도로
  읽혔거나, 취소)에는 다시 받지 않는다 — 그 점검은 판정불가로 남고 시험운전이
  열리지 않는다.
- 전환을 받아들이면 AI가 읽은 라벨 원본 표시(rpm·m/s 표기, 내경, 유효기한
  원문)로 **빈 자리만** 채운다. 이미 있는 표기(로컬 OCR이 읽은 것)는 덮지 않는다
  — 덮으면 그 표기가 올렸던 불일치가 사라질 수 있다. 채운 표시는 표기 일치·장착
  규격 항목을 새로 만들 수만 있다. 표기 일치의 통과는 전체 판정을 올리지 못하고,
  어긋나면 판정불가로 막는다. 위에서 버린 판독의 표시를 건지는 것이 아니다 —
  새로 읽어 확정한 값과 다른 값이 없음을 확인하고 받아들인 판독의 표시이고,
  처음부터 온라인으로 읽은 판독과 같은 자격으로 쓴다.
- 두 판독이 원본 표시의 **같은 칸을 다르게** 읽었으면(rpm 표기·m/s 표기·내경)
  제한 대조를 풀지 않는다. 덮지 않으면 앞선 표기가 조용히 이겨 서버가 읽은 표기가
  판정에서 빠지고, 덮으면 앞선 판독이 올린 표기가 사라진다. 어느 쪽이 맞는지 앱은
  모르므로 고르지 않는다. 한쪽이 읽지 못한 칸은 기권이고 충돌이 아니다. 저장소도
  그 재분석을 받지 않는다. 이 조건과 빈 자리 채움을 합치면 받아들인 표시가 서버가
  읽은 칸을 모두 담으므로, 표기 일치 판정이 처음부터 온라인으로 읽은 점검보다
  느슨해지지 않는다.
- 화면은 충돌한 칸만 비교표와 따로 보인다. 그 표기를 기기 안 OCR이 읽었다고 제한
  까닭에 남아 있으면 「기기 판독 / AI 값」이라고 적고, 까닭이 남아 있지 않으면
  「앞선 판독 / AI 값」이라고 적는다 — 읽을 때 기기가 오프라인으로 보고됐을 뿐인
  판독은 서버가 읽은 것일 수 있다(위 「제한 대조의 이름과 까닭」). 안내 문장은 두
  경우 모두 「앞서 읽은 라벨 표기」라고만 한다.
- 작업자가 확인 화면에서 확정한 값(회전속도·지름·두께·용도·종류·유효기한)은
  AI 값으로 바꾸지 않는다. 대신 **다르면 제한 대조를 풀지 않는다.** 회전속도·지름은
  AI가 읽지 못한 경우도 막는다. 용도·유효기한·종류는 양쪽 다 값이 있고 다를 때만
  막는다 — 처음부터 온라인이었다면 AI가 읽은 값이 확인 화면의 기본값이고 작업자가
  보면서 고쳐야 바뀌는데, 재분석 경로에는 그 장치가 없기 때문이다. 양쪽 다 종류를
  말했을 때의 다름은 확인 화면이 직접 확인을 요구하는 기준과 같다(세부 형식을
  고른 것은 다름이 아니다). 유효기한은 작업자가 `표시를 찾지 못함`이나
  `읽기 어려움`으로 답했는데 AI가 날짜를 읽은 경우도 다름이다 — 그 답 그대로
  제한 대조를 풀면 AI가 읽은 기한이 판정에서 빠진다.
- 한쪽에 견줄 값이 없으면 **기권**이고 막지 않는다. 화면에는 「견줄 값
  없음」으로 적는다. AI 쪽은 용도 미확인·기한을 읽지 못함·종류 모름이다. 확정값
  쪽은 용도·종류를 모르겠음으로 두었거나, 유효기한에 날짜도 답도 없는 경우다 —
  이런 확정값은 규칙엔진에서 이미 적합에 이르지 못한다(용도를 대조하지 않는 종류는
  AI가 읽은 용도로 대조해도 결과가 같다). 이 근거는 종류별 Profile 구성에 기대고
  있어 테스트로 고정해 두었다(`confirm.test.ts`).
- 서버가 그 사진을 **낮은 신뢰도**로 읽었으면(명판이든 숫돌 라벨이든) 값이 모두
  같아도 제한 대조를 풀지 않는다. 신뢰도는 모델이 주는 자기 경고이고, 처음부터
  온라인이었다면 낮은 신뢰도는 판정불가이며 작업자가 그 경고를 보면서 직접 확인해야
  풀린다. 재분석 경로에서 작업자의 직접 확인은 그 경고보다 **먼저** 한 것이고,
  로컬 OCR로 읽은 명판은 직접 확인 없이도 진행된다(로컬 OCR의 신뢰도는 값을 다
  읽었는지로만 정한다). 여기서 직접 확인을 다시 받지는 않는다 — 다시 촬영하면 확인
  화면이 그 경고와 직접 확인을 그대로 낸다. 신뢰도 보통은 막지 않는다. 규칙엔진이
  막는 것도 낮음뿐이다.
- 제한 대조를 푼 점검에서 판정에 쓴 표기가 기록된 OCR 원본과 다르면 판정 근거
  화면이 그 칸을 따로 보인다. OCR 원본 자리는 확정할 때의 판독 그대로이므로(아래
  「재분석 판독의 기록」) 다른 칸은 받아들인 재분석 판독이 **빈 자리를 채운**
  표기다. 그 값이 기록의 받아들인 판독이 읽은 값과 같으면 「받아들인 서버 재분석
  판독이 읽은 표기」라고 적는다 — 기록으로 확인되는 사실이다. 확정할 때의 판독이
  읽어 두고 서버가 읽지 못한 칸은 OCR 원본과 같아 여기 나오지 않는다. 그 숫자의
  출처는 OCR 원본에 그대로 있다. 어느 경우든 작업자가 확인한 값이 아니라고 함께
  적는다.
- 재분석 판독 칸이 생기기 전에 풀린 기록은 반대다. 서버 판독이 OCR 원본 자리를
  덮어 앞선 판독의 표기가 「다른 값」으로 나온다. 그 기록이 말해 주는 것은 두 값이
  다르다는 것까지라, 판정 근거 화면은 서버 재분석 전에 읽어 둔 표기로 **보인다**고만
  적는다. 한 칸이라도 받아들인 판독으로 설명되지 않는 기록도 같은 문장으로 적는다 —
  출처를 지어내지 않는다.

**재분석 판독의 기록.** 판정에 쓰지 않는 것과 버리는 것은 다르다. 재분석 판독은
받아들였든 아니든 기록(`InspectionRecord.reanalyses`)에 받은 순서대로 전부 남긴다.
판정은 이 칸을 보지 않는다.

- 판독마다 도착 시각, 다시 읽은 단계의 판독과 응답 메타데이터, 받아들인 시각,
  다시 받은 1번 항목의 답과 시각을 남긴다. 다시 읽지 않은 단계와 일어나지 않은
  일은 비워 둔다. 값이나 표기가 달라, 또는 낮은 신뢰도로 읽혀 전환이 막혔거나
  작업자가 취소한 판독도 남는다 — 그 판독이 올린 의심이 어디서 왔는지, 왜 풀리지
  않았는지 기록으로 되짚을 수 있어야 한다. 표기 충돌로 저장소가 받지 않은 판독도
  받아들인 시각 없이 남는다. 다시 분석해도
  앞선 판독을 지우지 않는다. 뒤의 판독이 의심하지 않아도 앞선 의심은 규격 값에
  남기 때문이다.
- OCR 원본 자리(`grinderOcr`·`wheelOcr`)에는 넣지 않는다. 그 자리는 작업자가 확인
  화면에서 고치기 전의 원본이다. 재분석 판독은 작업자가 값을 확정한 **뒤**에 왔고
  작업자가 고친 적이 없으며, 로컬 OCR로 읽은 점검이면 그 원본을 덮는다. 받아들인
  판독도 같다.
- 다시 받은 1번 항목의 답은 `확인함`이든 `문제 있음`이든 그 판독에 남긴다. 숫돌
  상태 확인의 답은 경고를 보기 전의 것이고 `확인함`으로 다시 답해도 값이 같아,
  따로 남기지 않으면 다시 물었다는 사실이 기록에서 보이지 않는다.
- 판정 사유 문장은 바꾸지 않는다. 받아들이지 않은 점검은 여전히 「확정한 값을
  뒷받침하는 서버 판독이 확인되지 않아 작업자가 확인한 값으로만 대조했습니다」로
  적힌다 — 대조는 실제로 그 값으로만 했고, 값이 달랐거나 취소한 판독은 확정한 값을
  뒷받침하지 않는다. 다만 그 문장은 서버가 사진을 다시 읽었는지를 말하지 않으므로,
  결과 화면·이력·기록 문서가 남아 있는 재분석 판독 수와 그 가운데 받아들인 수, 결과에
  반영한 것(외관 의심), 다시 받은 답을 판정 항목과 따로 적는다. 받아들인 판독은
  **어느 단계의 판독인지**로 적고, 점검 전체가 제한 대조를 벗어났다고 적지 않는다 —
  명판·숫돌을 함께 받아들인 뒤 숫돌만 서버 판독 없이 다시 확정하면 그 점검은 다시
  제한 대조이고, 남은 사실은 명판 판독을 받아들였다는 것뿐이다. 받은 수와 받아들인
  수도 따로 적는다. 값이 달라 막힌 판독까지 일치한 것처럼 읽히면 안 된다.
- 판독마다의 내역(판정 근거 화면·기록 문서)은 그때 화면이 보여 준 비교표
  (회전속도·지름·용도·유효기한·종류)와 표기 충돌, 낮은 신뢰도로 읽은 사진, AI 외관
  판독, 받아들였는지, 다시 받은 답을 적는다. 비교표는 결과 화면의 재분석 패널과 같은
  함수로 만든다 — 회전속도·지름이 모두 같은데도 풀지 않은 판독이 왜 막혔는지
  (용도·유효기한·종류의 차이, 표기 충돌, 낮은 신뢰도) 기록에서 보인다. 견주는 상대인
  확정값은 재분석을 받아들여도 바뀌지 않는다. 표기 충돌은 확정값이 아니라 **기록의
  OCR 원본**과 견준다 — 확인 화면은 그 판독의 표기를 그대로 확정값에 실었고 재분석은
  원본 자리를 건드리지 않으므로, 원본의 표기가 곧 그때 견준 상대다. 무엇이 읽었는지는
  풀린 뒤 까닭이 지워져 알 수 없으므로 「앞선 판독」이라고만 적는다.
- 재분석을 하지 않은 점검은 빈 목록을 남긴다. 이 칸이 없는 기록은 **알 수 없다** —
  칸이 생기기 전의 기록이거나, 그 전 버전에서 시작한 점검이다. 없는 칸을 빈 목록으로
  읽거나 채우지 않는다. 칸이 생기기 전에 재분석으로 제한 대조를 푼 기록은 OCR 원본
  자리에 서버 판독이 들어 있다. 그 기록은 옮기지 않고 그대로 읽는다.
- 한 점검에 남기는 판독은 20개까지다. 그만큼 받았으면 더 받지 않는다 — 남기지 못할
  판독을 받으면 그 판독이 올린 의심의 출처가 다시 사라진다. 오래된 판독을 밀어내지
  않는 것도 같은 이유다.
- 숫돌을 다시 확정하면 그 숫돌 사진을 본 판독과 그때 받은 답은 버린다(재촬영의
  기존 규칙과 같다). 명판 판독은 남는다. 응답을 기다리는 사이 다시 찍은 단계의
  판독도 남기지 않는다 — 이 점검의 명판·숫돌을 본 판독이 아니다.

남는 한계. 고치려면 따로 정해야 한다.

- 로컬 OCR 빌드에서는 작업자가 확인 화면에서 오독을 고친 숫돌도 제한 대조가
  풀리지 않는다. 확인은 정규화 값만 바꾸고 원본 표기는 그대로 두므로, 그 표기가
  서버 판독과 충돌한다. 다시 촬영해도 로컬 OCR이 같은 오독을 내면 계속 제한
  대조(판정불가)로 남는다. 알고 받아들인 것이다(2026-10-04) — 피하려면 로컬 표기를
  서버 값으로 덮어야 하고, 그것은 이미 올라온 표기를 지우는 방향이다. 직접 입력한
  숫돌에는 원본 표기가 없어 이 한계가 없다.
- 확정값의 차이(용도·유효기한·종류)와 낮은 신뢰도도 로컬 OCR 빌드에서는 다시
  촬영으로 풀리지 않을 수 있다. 다시 찍어도 로컬 OCR을 거쳐 같은 길로 돌아오므로,
  AI가 같은 값을 매번 다르게 읽거나(예: 절단·연삭이 함께 적힌 라벨) 매번 낮은
  신뢰도로 읽으면 그 점검은 계속 제한 대조로 남는다. 서버로 읽는 빌드에서는 다시
  촬영하면 확인 화면이 AI 값과 신뢰도를 보이므로 작업자가 보면서 고치고 직접
  확인할 수 있다.
- 서버가 숫자는 맞게 읽으면서 신뢰도만 낮음으로 내는 빈도는 재지 않았다. 잦다면
  재분석으로 제한을 푸는 길이 그만큼 좁아진다. 재분석 판독은 신뢰도까지 기록에
  남으므로 기록에서 셀 수는 있다(CSV에는 그 열이 없다).
- AI가 읽지 못한 용도·유효기한·종류는 견주지 않았을 뿐이다. AI가 그 값을 확인해
  준 것이 아니다. 두께는 판정에 쓰이지 않아 견주지 않는다.
- 풀린 단계의 제한 까닭은 지워진다(위 「제한 대조의 이름과 까닭」). 그 단계를
  확정할 때의 판독은 OCR 원본 자리에 그대로 남고 무엇이 읽었는지도 응답
  메타데이터(엔진)에 남지만, 「직접 입력」과 「버린 판독」은 OCR 원본이 없어 풀린
  기록에서 서로 구분되지 않는다.
- 저장소가 스스로 막는 것은 둘뿐이다 — 도착했을 때 남기지 않은 판독과 표기 충돌.
  확정값의 차이·낮은 신뢰도·손상 항목 재확인은 결과 화면(`OfflineReanalysisPanel`)이
  막는다.
- 판독마다의 내역(판정 근거 화면·기록 문서)이 적는 표기 충돌은 **OCR 원본이 남은
  기록에서만** 나온다. OCR 원본을 남기지 않은 확정값(버린 판독, 일부 값만 모름으로
  읽은 판독)은 견줄 원본이 없어 적지 않는다 — 그런 기록에서 표기 충돌로만 막힌
  판독은 「풀지 않음」으로만 보인다. 저장된 확정값의 표기와 견주지 않는 까닭은, 뒤에
  다른 판독을 받아들이면 그 표기의 빈 자리가 채워져 그때 없던 충돌이 생겨 보이기
  때문이다. 판독이 읽은 표기 자체는 기록에 남아 있다.
- 실패한 재분석(서버에 닿지 못했거나 오류)은 판독이 없어 기록에 남지 않는다.
  남아 있는 판독 수는 서버를 부른 횟수가 아니다.
- 20개를 채운 뒤에는 화면이 재분석을 받지 않는다. 그 막음을 거치지 않고 판독이
  들어오면 판독은 남기지 못하고 의심만 남는다 — 경고를 버리지 않는 쪽을 골랐다.
  저장 공간이 모자라 판독 목록을 새로고침용으로 남기지 못한 경우도 같다. 새로고침
  뒤 목록은 「알 수 없음」이 되고 의심은 규격 값에 남는다.
- 판독에는 OCR 원문이 들어 있다(OCR 원본과 같은 모양). 화면·기록 문서·CSV에는
  싣지 않지만, 기기 안 기록과 백업 파일에는 판독 수만큼 늘어난다.
- 재분석 판독은 평가 지표(필드 추출 정확도·정정률)에 넣지 않는다. 기록과 CSV의
  재분석 열에서 따로 본다([validation-plan.md](validation-plan.md)).
- 재분석 판독 칸이 생기기 전에 제한 대조를 푼 기록은 OCR 원본 자리가 서버 판독으로
  바뀌어 있다. 그 기록에서는 재분석 전의 OCR 원본이 남아 있지 않고, 최고사용
  회전속도의 출처(`rpmSource`)는 확정할 때의 판독 기준이라 판정 근거 화면의 그 줄이
  서로 다른 판독을 가리킬 수 있다.
- `문제 있음`으로 답한 뒤 숫돌을 다시 찍으면 새 사진의 판독과 답으로 처음부터
  다시 한다. 앞선 의심과 답은 이어지지 않는다(재촬영의 기존 규칙과 같다).

계층 관계는 위 「네 계층」에 한 번만 적는다.

## 시험운전 (제122조 ②)

규격이 맞고 두 Gate와 체크리스트가 모두 끝난 뒤에만 시작할 수 있다.
부적합·판정불가 조합의 시험운전을 앱이 유도하면 그 자체가 사고 경로다.

작업 시작 전 1분 이상, 숫돌 교체 후 3분 이상. 남은 시간은 **절대 종료시각**
에서 계산한다 — 틱을 세면 화면이 멈춘 만큼 시간이 짧아져, 앱이 법이 정한
시간을 마음대로 줄이는 셈이 된다.

타이머가 끝나면 작업자가 다섯 가지(진동·소음·흔들림·파손 징후·장비 이상)를
직접 답한다. AI는 어느 것도 판별하지 못하고 대신 고르지도 않는다. 이상이
확인되면 작업 중지 안내를 띄우고 저장 문구가 「중지 결과 저장」으로 바뀐다.
문제가 확인된 결과를 「점검 완료」라고 부르지 않는다.

**이 앱은 시간을 재고 답을 남길 뿐이다.** 법정 절차를 대신한다거나 시간을
줄여준다고 말하지 않는다.

## 최종 체크리스트에 남는 것

방호덮개·보조손잡이는 Grinder Condition Gate로, 숫돌 손상은 Wheel Condition
Gate로 옮겼다. **같은 것을 두 번 묻지 않는다** — 두 번째는 읽지 않고 누르게
되고, 그 순간 체크는 확인이 아니라 절차가 된다.

최종 체크리스트에는 보호구 착용, 작업물 고정, 주변 사람·가연물 확인이 남는다.
기계도 숫돌도 아닌 **사람과 작업 환경**이라 어느 Gate에도 속하지 않는다.
불꽃 방향은 매 순간 달라지는 항목이라 체크박스로 만들지 않고 작업 직전
안내로 둔다.

과거 기록을 읽을 수 있도록 `SafetyChecklist` 필드와 CSV 열은 지우지 않는다.
화면에서 빼는 것과 저장 구조에서 지우는 것은 다르다.

## 연구 결과를 말할 때

발표·논문에서도 같은 경계를 지킨다.

- 규칙엔진 테스트 개수와 **실물 촬영 세트 수**를 섞어 말하지 않는다.
  전자는 합성 값 로직 검증, 후자는 실험이다.
- "판정 오류"와 "인식 오류"를 나눠 보고한다. 판정이 결정론적 규칙이므로
  **부적합 탐지 재현율 = 필드 추출 정확도**다.
- 직접 확인한 것만 확인했다고 말한다. 실기기 카메라, 배포, 실제 인식률은
  각각 따로 확인해야 한다.

측정 방법은 [validation-plan.md](validation-plan.md)에, 실물 검증 절차는
[rc-field-validation.md](rc-field-validation.md)에 있다.
