# 검증 계획

**무엇을 어떻게 재는지**를 정한다. 일정은 [roadmap.md](roadmap.md)에 있다.
실물 20세트의 실행 절차·표본 구성·합격 기준은 [rc-field-validation.md](rc-field-validation.md)에 있다.
실행 중 기록에는 [조원용 측정 기록지](field-session-sheet.md)를 사용한다.

측정 전에 이 문서를 읽고, 측정 후에 실제로 한 방식과 다르면 **이 문서를 고친다.**
논문에 적을 방법은 여기에 적힌 것이어야 한다.

---

## 무엇을 재야 하는가

**인식 성능과 판정 성능은 별도로 측정한다.** 결정론적 규칙은 같은 입력에 같은
결과를 내지만, 규칙의 누락·잘못된 적용·화면에서 전달되지 않은 입력까지 없다는
뜻은 아니다. 필드 추출이 맞아도 판정은 틀릴 수 있다.

필드 추출 정확도는 정답이 있는 **필드 수**를 분모로 한다. 부적합 탐지 재현율은
정답이 부적합인 **점검 건수**를 분모로 하며, 그중 앱이 부적합으로 판정한 비율이다.
두 값은 같지 않다. 예를 들어 4개 필드 중 1개를 오독해도 RPM 위반을 올바르게
잡을 수 있고, 4개를 모두 읽어도 작업 목적 검사가 빠지면 부적합을 놓칠 수 있다.

정답이 부적합인 건에서 `UNDETERMINED`로 멈춘 경우는 부적합 탐지 성공이나
False-Safe로 합치지 않고 별도로 보고한다. 재현율과 False-Safe Rate는 서로의
여집합이 아니다. 저장 전에 막히거나 저장하지 못한 사례도 현장 기록지에 남긴다.
정답 판정은 검증 대상 엔진의 출력을 복사하지 않고 독립적으로 정한다.

| 지표                 | 정의                                                                                                   | 어디서 나오나                       |
| -------------------- | ------------------------------------------------------------------------------------------------------ | ----------------------------------- |
| **필드 추출 정확도** | 모델 원본값 == 정답값인 필드 비율                                                                      | CSV `*_ocr` 열 vs 정답              |
| **정정률**           | 사용자가 값을 고친 기록 비율                                                                           | CSV `grinderEdited` / `wheelEdited` |
| **판정불가율**       | `UNDETERMINED` 비율                                                                                    | CSV `verdict`                       |
| **False-Safe Rate**  | 실제 부적합인데 `COMPATIBLE`로 나온 비율. 분모는 정답이 부적합인 기록 수                               | CSV `verdict` vs 정답 판정          |
| **사전점검 시간**    | 작업 선택 ~ 시험운전 시작 직전 (ms). 시험운전이 열리지 않으면 저장까지. 「30초」 목표는 이 값으로 잰다 | CSV `preTrialElapsedMs`             |
| **전체 흐름 시간**   | 작업 선택 ~ 저장 (ms). 적합 세트는 법정 시험운전이 들어 있다                                           | CSV `elapsedMs`                     |
| **사용성**           | SUS 점수                                                                                               | 설문                                |

**False-Safe Rate가 0이어야 한다.** 0이 아니면 그 사례를 개별로 분석해 보고한다.
숨기지 않는다.

비율은 항상 분자·분모와 함께 적는다. **분모가 0이면 `N/A`로 적는다** — 재지 않은 것을
`0%`로 적으면 달성한 것으로 읽힌다.

## 1. 실물 20세트 측정

절차는 [rc-field-validation.md](rc-field-validation.md)를 따른다. 이 절은 무엇을 남겨야 하는지만 적는다.

### 준비

- 그라인더 여러 대 + 숫돌 여러 종 (절단·연삭 섞어서)
- **정답 기록지** — 촬영 전에 사람이 라벨을 직접 읽어 적는다
- **검증 빌드**(`NEXT_PUBLIC_ENABLE_RESEARCH_TOOLS=true`)의 이력 화면 맨 아래에서
  연구·실험 모드를 켠다. 현장 배포판에는 이 패널이 없다. 기록은 주소·기기마다 따로
  저장되므로 처음부터 검증 빌드에서 진행한다

### 정답(Ground Truth)을 먼저 적는다

앱을 켜기 **전에** 종이나 별도 파일에 적는다. 앱 결과를 보고 나서 정답을
적으면 앱에 끌려간다.

세트마다 적을 것:

| 항목                      | 예                |
| ------------------------- | ----------------- |
| 세트 번호                 | 07                |
| 그라인더 모델             | GWS 750-125       |
| 그라인더 무부하 회전속도  | 11000 rpm         |
| 그라인더 최대 숫돌 지름   | 125 mm            |
| 숫돌 최고사용회전속도     | 12200 rpm         |
| 숫돌 지름 / 두께 / 내경   | 125 / 1.6 / 22.23 |
| 숫돌 용도                 | 절단              |
| **사람이 내린 정답 판정** | 적합              |
| 촬영 조건                 | 실내·형광등       |

**촬영 조건을 반드시 적는다.** 실패 사례를 나중에 설명할 수 있는 유일한 단서다.

정답 판정은 이 앱의 규칙을 사람이 실물 값에 적용한 결과다. 작업 안전에 대한 판단이
아니다. 절차는 [rc-field-validation.md](rc-field-validation.md) §4.

### 촬영

- 세트당 **최소 1회**, 가능하면 조건을 바꿔 2회 (밝은 곳 / 어두운 곳)
- 값을 고쳐야 하면 **고친다.** 고친 기록 자체가 정정률 데이터다
- 판정불가가 나와도 그대로 저장한다. 지우지 않는다

### 내보내기

검증 빌드의 이력 화면 → 연구·실험 모드 → CSV 내려받기.
파일명에 시각이 붙으므로 여러 번 뽑아도 덮어쓰이지 않는다.

### 주의

- 자동 테스트 개수는 **20세트와 다른 것**이다.
  전자는 합성 값 로직 검증, 후자는 실물 촬영 실험이다. 섞어 말하면 지적당한다.
- 원본 OCR 객체를 보관하지 않은 기록은 해당 쪽(그라인더/숫돌)의 필드 정확도에서만
  제외한다. 원본 객체는 있으나 특정 값이 `null`이고 정답값이 있으면 **미인식**으로 센다.
  CSV의 빈 칸만으로 두 경우를 구분하거나 기록 전체를 제외하지 않는다.

### 평가 계산의 분모

- 필드 정확도: 해당 원본 OCR 객체와 정답값이 모두 있는 필드 수. 원본에 실제로
  남은 `null`은 미인식, 다른 숫자는 오독이다. 작업자가 고친 최종값은 쓰지 않는다.
- 환산 RPM 불일치율(평가 화면 표기 「단위 정규화 오류」): 원본의 `rpmSource=converted`이고
  정답 RPM이 있는 기록 수.
  정답 RPM이 없는 사례는 분자·분모에서 제외한다. 이 수치만으로 m/s·지름 오독과
  산술 환산 오류를 구분할 수 없으므로, 원인은 개별 기록으로 따로 분석한다.
- 판정불가율: 정답과 연결된 기록 중 `UNDETERMINED`인 비율이다. 미인식뿐 아니라
  제한적 Profile·오프라인 등도 포함되므로 이를 OCR 실패율이라고 부르지 않는다.
- 모든 비율은 분모가 0이면 계산 함수에서도 `null`, 화면에서는 `N/A`다.

계산 대상은 **저장된 기록 중 정답과 연결된 표본**이다. 전체 시도 성공률이나
실물 안전성을 증명하는 값이 아니다. 저장 전에 차단·중단된 시도는 별도 기록지의
전체 시도 수에 포함하고, 실물 촬영과 합성 이미지 결과는 별도로 집계한다.

## 2. 소요시간 비교 (수기 vs 앱)

같은 사람이 같은 세트를 두 방식으로 점검하고 시간을 잰다.

| 방식 | 재는 법                                                  |
| ---- | -------------------------------------------------------- |
| 수기 | 초시계. 라벨 확인 ~ 점검표 작성 완료까지                 |
| 앱   | CSV `preTrialElapsedMs` (작업 선택 ~ 시험운전 시작 직전) |

**공정하게 재기 위해:**

- 순서 효과를 없애려면 절반은 수기 먼저, 절반은 앱 먼저
- 앱 쪽 시간에는 촬영·분석 대기 시간이 포함된다. 빼지 않는다
- 앱은 사전점검 시간(`preTrialElapsedMs`)으로 견준다. 적합 세트의 전체 흐름 시간
  (`elapsedMs`)에는 법정 시험운전(60초·180초 이상)이 들어 있어 수기 점검과 견줄 수 없다
- 처음 몇 세트는 익숙해지는 시간이라 따로 표시해 둔다

「30초」는 **사전점검 시간**(`preTrialElapsedMs`, 작업 선택 ~ 시험운전 시작 직전)의 목표다.
법정 시험운전 시간은 이 목표와 별도이며, 목표 때문에 줄이지 않는다. 달성하지 못하면 그대로 보고한다.

## 3. SUS 설문 (5~10명)

- 표준 SUS 10문항을 그대로 쓴다. 문항을 임의로 바꾸면 점수를 비교할 수 없다
- 앱을 **실제로 한 번 이상 써 본 뒤** 답하게 한다
- 응답자 배경(직무·경력·외국인 여부)을 함께 기록한다
- 인원이 적으므로 평균과 함께 **개별 점수를 모두** 싣는다

## 4. 실기기 확인 (코드로 못 채우는 것)

브라우저 개발 도구로는 확인할 수 없는 것들이다. **실기기에서만** 확인한다.

| 항목                | 확인 방법                                    |
| ------------------- | -------------------------------------------- |
| 카메라 촬영 경로    | 실제 휴대폰에서 촬영 → 분석까지              |
| 갤러리 업로드 경로  | 12MP 원본 사진으로 시도 (4.5MB 한도 확인)    |
| CSV 파일 저장       | 폰에서 실제로 파일이 떨어지는지              |
| QR 스캔 후 브라우저 | 인앱 브라우저(카톡 등)에서 카메라가 막히는지 |
| 오프라인 동작       | 비행기 모드에서 화면이 뜨는지 (PWA)          |

확인한 날짜와 기기명을 함께 적는다. 새로고침·시험운전 복구·연구 도구 비노출까지 포함한
기기·흐름 시험 목록은 [rc-field-validation.md](rc-field-validation.md) §6에 있다.

## 5. 보고할 때

- 직접 확인한 것만 확인했다고 말한다
- 실패 사례를 빼고 보고하지 않는다. 20세트 중 3세트가 판정불가였다면 그대로 적는다
- 판정불가는 **실패가 아니라 설계된 동작**이다. 그렇게 설명한다
- 표현 경계는 [safety-boundaries.md](safety-boundaries.md)를 따른다
