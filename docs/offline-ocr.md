# API 없이 돌아가게 만들 수 있을까

2026-09-01 실측 기록.

결론부터: **이미 절반은 되어 있고, 나머지 절반이 어렵다.**
판정은 처음부터 API가 필요 없었고, 문제는 라벨을 읽는 단계뿐이다.

## 이 앱의 구조가 유리한 이유

```
촬영 → [라벨 읽기]  →  사용자 확인 → [판정] → 적합/부적합/판정불가
         AI 필요                    순수 TypeScript
```

`src/lib/rules/engine.ts`는 외부 의존성이 없는 순수 함수다. 그래서
**판정 로직은 이미 100% 오프라인**이다. 교체 대상은 라벨 읽기 한 곳뿐이고,
`OCRExtractor` 인터페이스로 이미 분리해 두었다.

## 실측: Tesseract.js vs Claude

`NEXT_PUBLIC_OCR_MODE=tesseract`로 전환해 같은 이미지로 비교했다.

### 깨끗한 라벨 (정면, 고대비, 인쇄체)

| 항목                      | Tesseract (API 없음) | Claude           |
| ------------------------- | -------------------- | ---------------- |
| 모델명                    | `GWS 750-125` ✅     | `GWS 750-125` ✅ |
| 무부하 회전속도           | `11000` ✅           | `11000` ✅       |
| 허용 지름                 | `125` ✅             | `125` ✅         |
| 숫돌 라벨 (m/s 환산 포함) | `12223` ✅           | `12223` ✅       |
| 소요 시간                 | **1.0초**            | 3~4초            |
| 네트워크                  | **0회**              | 1회              |
| 비용                      | **0원**              | 호출당 과금      |

깨끗한 조건에서는 Tesseract가 **더 빠르고 무료이며 정확도가 같다.**

### 현장 사진 흉내 (6도 기울임 + 반사광 + 노이즈 + 낮은 대비)

| 항목            | Tesseract        | Claude           |
| --------------- | ---------------- | ---------------- |
| 모델명          | `BO 0000` ❌     | `GWS 750-125` ✅ |
| 무부하 회전속도 | 읽지 못함 (null) | `11000` ✅       |
| 허용 지름       | 읽지 못함 (null) | `125` ✅         |
| 소요 시간       | 13.2초           | 5.4초            |

**여기서 갈린다.** 금속 명판은 각인이라 대비가 낮고, 손으로 들고 찍으면
반드시 기울고, 실내조명은 반사를 만든다. 실제 현장 조건이다.

Tesseract가 실패했을 때 값을 지어내지 않고 `null`로 남겨 판정불가로
이어진 것은 설계대로다. 하지만 "판정불가"만 계속 나오는 앱은 쓸모가 없다.

## 그래서 가능한가

가능하다. 다만 Tesseract를 그대로 쓰는 방식으로는 안 된다.

### 단계 1 — 전처리 (며칠, 효과 큼)

Tesseract는 전처리에 매우 민감하다. 지금은 원본을 그대로 넘기고 있다.

- 기울기 보정 (deskew)
- 적응형 이진화 (Otsu / Sauvola) — 반사광 대응
- 대비 스트레칭, 노이즈 제거
- 텍스트 영역만 잘라내기

OpenCV.js로 브라우저에서 가능하다. 위 실패 사례 중 상당수가 여기서 살아난다.
**투자 대비 효과가 가장 크므로 여기부터 한다.**

### 단계 2 — 더 나은 OCR 모델 (1~2주)

Tesseract는 스캔 문서용으로 만들어졌고 자연 사진에 약하다.
사진 속 글자(scene text)에는 다른 모델이 쓰인다.

- **PP-OCR 계열 모바일 모델** — ONNX Runtime Web으로 브라우저 실행.
  검출 + 인식 합쳐 10MB 안팎. 기울기·곡면·저대비에 Tesseract보다 강하다.
- 서비스 워커로 캐시하면 첫 방문 후 완전 오프라인.

### 단계 3 — 이 도메인에 맞춘 학습 (수개월, 데이터 필요)

여기가 진짜 연구 주제다.

- 필요한 것: 실제 그라인더 명판·숫돌 라벨 사진 **수백~수천 장 + 정답 라벨**
- 읽어야 할 것은 자유 문장이 아니라 **정해진 패턴**이다
  (`\d{4,5}\s*(r/min|rpm)`, `Φ\d{2,3}mm`, `\d+\s*m/s`)
- 패턴이 좁으므로 범용 OCR보다 작은 모델로도 높은 정확도가 가능하다
- 데이터 수집이 전체 일정의 대부분을 차지한다

## 현실적인 권장안 — 하이브리드

둘 중 하나를 고르는 문제가 아니다.

```
사진 → 전처리 → 온디바이스 OCR
                    ├─ 신뢰도 높음 → 그대로 사용 (무료·1초·오프라인)
                    └─ 신뢰도 낮음 → Claude 호출 (정확·유료)
                                        └─ 그것도 실패 → 판정불가 + 수동 입력
```

이 구조의 장점:

- 깨끗한 라벨(대다수)은 공짜로, 빠르게, 오프라인으로 처리된다
- 어려운 사진만 API를 쓰므로 비용이 크게 준다
- 네트워크가 끊겨도 앱이 죽지 않는다
- **어느 경로든 판정은 같은 규칙엔진이 한다** — 안전 로직은 하나뿐이다

`OCRExtractor` 인터페이스가 이미 있으므로 `HybridExtractor`를 하나 더
만들면 되고, UI는 건드리지 않아도 된다.

## 학술대회에서 말할 수 있는 것

- 안전 판정을 AI에서 분리한 설계 덕분에 **OCR 엔진 교체가 UI·판정에 영향을 주지 않는다**
- 같은 이미지로 두 엔진을 실측 비교한 데이터가 있다
- 온디바이스 OCR의 실패가 "오답"이 아니라 "판정불가"로 이어지도록
  설계되어 있어, 엔진을 바꿔도 안전 수준이 유지된다

## 재현 방법

```bash
NEXT_PUBLIC_OCR_MODE=tesseract npm run dev
```

전환은 환경변수 하나다. 코드 변경이 필요 없다.
