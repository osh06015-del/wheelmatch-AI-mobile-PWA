# RC 현장 검증 실행계획 — 실물 20세트

출시 후보(Release Candidate)를 **사람이 실제 장비와 라벨로** 확인하는 절차다.
이 문서는 절차와 기록 양식만 정한다. **결과와 수치는 적혀 있지 않다.**

| 알아야 할 때                    | 문서                                            |
| ------------------------------- | ----------------------------------------------- |
| 지표를 무엇으로 정의하나        | [validation-plan.md](validation-plan.md)        |
| 화면·보고서에 쓰면 안 되는 표현 | [safety-boundaries.md](safety-boundaries.md)    |
| 규칙 12종의 조건                | README 「판정 규칙」, `src/lib/rules/engine.ts` |
| 키가 노출됐을 때                | [SECURITY.md](../SECURITY.md)                   |

## 이 문서를 쓰는 규칙

- **실행하지 않은 항목은 「미실시」로 적는다.** 통과로 적지 않는다. 빈칸도 통과가 아니다.
- **앱이 무엇을 낼지 미리 적지 않는다.** 표본 표에는 준비할 실물 조건만 있다.
- **분모가 0이면 비율 칸에 `N/A`를 적는다.** `0%`로 적지 않는다.
- 비율은 항상 `분자 / 분모`와 함께 적는다.
- 실패·미실시·저장하지 못한 세트를 빼고 보고하지 않는다.
- 자동 테스트 통과는 이 검증을 대신하지 않는다. 합성 값 검증과 실물 실험은 다른 것이다.

## 0. 안전 — 시작 전에 참여자 모두 읽는다

이 검증은 **앱**을 시험한다. 작업이 안전한지를 시험하지 않는다.

- **부적합 조합·손상 의심·유효기한 경과·미지원 숫돌은 장착하지 않고 돌리지 않는다.**
  촬영과 화면 입력까지만 한다. 명판과 라벨을 따로 찍어 조합한다.
- **시험운전은 사람이 확인한 적합 조합에서만**, 사업장 안전수칙에 따라 자격 있는
  사람이 실제로 한다. 실제로 돌리지 않았으면 「이상 없음 확인」을 누르지 않는다(§3-3).
- **상태 확인과 체크리스트는 사실대로 답한다.** 결과를 보려고 거짓으로 통과시키면
  그 기록은 검증 데이터가 아니다. 앱이 막아야 할 길을 사람이 열어 준 것이 된다.
- 앱이 적합을 보여줘도 사람이 따로 확인한다. 이 앱은 규격끼리 맞는지만 대조하며
  **안전을 승인하지 않는다.**

## 1. 준비

### 1-1. 빌드 두 가지

| 빌드        | 설정                                                      | 이 계획에서 쓰는 곳                       |
| ----------- | --------------------------------------------------------- | ----------------------------------------- |
| 현장 배포판 | `NEXT_PUBLIC_ENABLE_RESEARCH_TOOLS` 없음                  | 기기·흐름 시험(§6), 연구 도구 비노출 확인 |
| 검증 빌드   | `NEXT_PUBLIC_ENABLE_RESEARCH_TOOLS=true`로 따로 빌드·배포 | 표본 20세트, CSV, 평가 지표               |

- 두 빌드는 **같은 커밋**이어야 한다. 배포 담당자가 두 배포의 커밋 해시를 적고,
  조작자는 결과 화면의 「규칙 버전」을 적는다.
- `NEXT_PUBLIC_` 값은 빌드할 때 번들에 박힌다. 설정을 바꿨으면 다시 빌드·배포한다.
- 검증 빌드의 이력 화면 맨 아래에 **「검증/연구용 기능이며 현장 판정을 변경하지
  않습니다.」** 가 보여야 한다. 안 보이면 검증 빌드가 아니다. 거기서 멈춘다.
- 검증 빌드 주소를 현장 작업자에게 주지 않는다. 휴대폰에서 검증 빌드 주소가 로그인
  화면으로 넘어가면 배포 보호 설정 문제이니 배포 담당자에게 알린다.
- **표본 20세트는 처음부터 끝까지 검증 빌드 주소에서 진행한다.** 기록은 주소마다·
  기기마다·브라우저마다 따로 저장된다. 현장 배포판에서 저장한 기록은 검증 빌드에서
  보이지 않는다. 홈 화면에 추가한 앱과 브라우저 탭도 저장 공간이 따로일 수 있다
  (특히 iPhone). **기록을 남긴 곳에서 CSV까지 내보낸다.**

### 1-2. 기기

- Android 1대 이상(Chrome), iPhone 1대 이상(Safari). 기기명·OS·브라우저 버전을 적는다.
- **날짜·시간 자동 설정을 켠다.** 유효기한 비교의 기준일은 결과 화면을 연 순간의 기기 날짜다.
- 20세트는 한 기기(주 기기)에서 끝낸다. 다른 기기는 §6 기기 시험과 표본 일부 반복에 쓴다.
- 기록 id는 기기마다 따로 붙는다. **정답 JSON도 기기별로 따로 만든다.**
- 시작 전에 주 기기의 이력을 본다. 기록이 있으면 CSV를 한 번 내보내 마지막 `id`를
  적어 둔다. 지울 필요는 없다.

### 1-3. 시험 작업대

체크리스트 3항목을 **사실대로** 확인할 수 있게 실제로 갖춘다.

- 보호구 착용 (보안경·장갑·안면보호구)
- 바이스·클램프로 고정한 작업물
- 불티가 닿는 범위에 사람·인화물질·가연물 없음

갖추지 못한 항목은 체크하지 않는다. 그러면 저장이 열리지 않는다 — 그 세트는
「저장 안 함(체크리스트 미충족)」으로 적는다.

### 1-4. 역할

| 역할          | 하는 일                                                         |
| ------------- | --------------------------------------------------------------- |
| 정답 기록자   | 앱을 켜기 전에 실물 라벨·명판을 읽어 정답 기록지(§3-1)를 채운다 |
| 조작자        | 앱을 조작하고 진행 기록지(부록 A)를 채운다                      |
| 시험운전 담당 | 적합 세트의 시험운전을 사업장 수칙대로 실제로 한다              |

**정답 기록자와 조작자는 가능하면 다른 사람으로 둔다.** 정답을 아는 사람이 값 확인
화면을 보면 실제 현장보다 잘 고친다. 같은 사람이 했다면 보고서에 그렇게 적는다.

### 1-5. 실물

- 휴대용 그라인더 여러 대. **최대 숫돌 지름이 다른 기종**을 섞는다(RC-M03). 명판이
  읽혀야 하고, 장비 상태가 좋아야 그라인더 상태 확인을 사실대로 통과할 수 있다.
- 숫돌은 §2 표의 조건대로 준비한다.
- **RC-F01·F03·F04·F05를 뺀 모든 숫돌은 라벨에 유효기한(월/연)이 인쇄돼 있고 지나지
  않은 것**이어야 한다. 유효기한 표시가 없으면 숫돌 상태 확인 5번을 사실대로
  「확인함」으로 답할 수 없고, 규칙엔진도 적합으로 가지 않는다(판정불가).
- 조건에 맞는 실물을 구하지 못하면 그 표본은 「미실시」다. 비슷한 것으로 바꿨다면
  「대체」라고 쓰고 무엇이 달랐는지 적는다.
- 표본 ID 카드(종이) 20장.

## 2. 표본 20세트

표에 **앱의 예상 결과는 없다.** 「보는 것」은 이 표본을 넣은 이유다.

### N — 정상 호환 5세트

사람이 실물을 읽었을 때 §4에서 `COMPATIBLE`이 나오는 조합. 선명한 라벨·명판을 밝은
곳에서 찍는다. 시험운전까지 실제로 한다.

| 표본 ID | 준비할 실물                                         | 입력   | 보는 것                                                       |
| ------- | --------------------------------------------------- | ------ | ------------------------------------------------------------- |
| RC-N01  | 절단용 결합숫돌 + 맞는 그라인더, 오늘 작업 「절단」 | 카메라 | 절단 흐름 끝까지                                              |
| RC-N02  | 연삭용 결합숫돌 + 맞는 그라인더, 오늘 작업 「연삭」 | 카메라 | 연삭 흐름 끝까지                                              |
| RC-N03  | 라벨에 rpm과 m/s가 **둘 다** 인쇄된 숫돌            | 카메라 | 두 표기 대조(표기 일치)                                       |
| RC-N04  | 라벨에 m/s만 있고 rpm 표기가 없는 숫돌              | 갤러리 | m/s → rpm 환산. 못 구하면 단위 정규화 오류는 N/A가 될 수 있다 |
| RC-N05  | 숫돌 지름 = 그라인더 최대 숫돌 지름                 | 카메라 | 지름 경계 (같으면 통과)                                       |

### M — 불일치 5세트

**장착하지 않는다.** 명판과 라벨을 따로 찍는다. 불일치 한 가지 외의 조건은 맞춘다.

| 표본 ID | 준비할 실물                                      | 입력   | 보는 것                                      |
| ------- | ------------------------------------------------ | ------ | -------------------------------------------- |
| RC-M01  | 숫돌 최고사용회전속도 < 그라인더 무부하 회전속도 | 카메라 | RPM 위반                                     |
| RC-M02  | M01과 **다른** 그라인더·숫돌로 만든 RPM 위반     | 갤러리 | RPM 위반 두 번째                             |
| RC-M03  | 숫돌 지름 > 그라인더 최대 숫돌 지름              | 카메라 | 지름 위반                                    |
| RC-M04  | 오늘 작업 「연삭」 + 절단용 숫돌                 | 카메라 | 목적 위반 — 얇은 절단날을 옆면으로 쓰는 경우 |
| RC-M05  | 오늘 작업 「절단」 + 연삭용 숫돌                 | 카메라 | 목적 위반                                    |

### R — 판독 곤란 5세트

**실물 라벨·명판은 사람이 읽을 수 있어야 한다.** 사진 조건만 나쁘게 만든다.
5세트 중 **최소 2세트는 사람이 읽었을 때 부적합인 조합**으로 준비한다 — 부적합 조합이
없으면 잘못 읽어서 적합으로 넘어가는 경우를 볼 수 없다. 부적합 조합은 장착하지 않는다.

| 표본 ID | 사진 조건                                            | 준비할 조합    | 보는 것                                    |
| ------- | ---------------------------------------------------- | -------------- | ------------------------------------------ |
| RC-R01  | 흐림 — 숫돌 라벨에 초점이 안 맞거나 손이 흔들린 사진 | RPM 위반 조합  | 숫돌 rpm을 **높게** 읽는지                 |
| RC-R02  | 반사 — 명판 숫자 위에 조명이나 햇빛 반사             | RPM 위반 조합  | 그라인더 rpm을 **낮게** 읽는지             |
| RC-R03  | 부분 잘림 — 숫돌 라벨의 지름 표기 일부가 화면 밖     | 지름 위반 조합 | 숫돌 지름을 **작게** 읽는지                |
| RC-R04  | 저조도 — 어두운 곳에서 플래시 없이, 명판과 라벨 모두 | 호환 조합      | 못 읽은 값이 비어 있는지 (채워지지 않는지) |
| RC-R05  | 비스듬한 각도, 또는 기름·먼지가 묻은 명판            | 호환 조합      | 기울기·오염                                |

세 방향(그라인더 rpm 낮게, 숫돌 rpm 높게, 숫돌 지름 작게)은 잘못 읽으면 **조용히
적합이 되는** 방향이다.

### F — Fail-safe 5세트

**장착하지 않고 돌리지 않는다.**

| 표본 ID | 준비할 실물                                                    | 보는 것                                                    |
| ------- | -------------------------------------------------------------- | ---------------------------------------------------------- |
| RC-F01  | 유효기한(월/연)이 **지난** 결합숫돌                            | 어느 층에서 멈추는지                                       |
| RC-F02  | 깨짐·잔금·모서리 파손이 눈에 보이는 **폐기 대상** 숫돌. 촬영만 | 손상 의심 경고가 떴는지(관찰), 「손상 없음」 표시가 없는지 |
| RC-F03  | 다이아몬드 절단날                                              | 적합으로 넘어가지 않는지                                   |
| RC-F04  | 플랩디스크 또는 컵휠 (무엇인지 적는다)                         | 적합으로 넘어가지 않는지                                   |
| RC-F05  | 최고사용회전속도 표기가 **실물에서도** 지워졌거나 없는 숫돌    | 값을 지어내지 않는지                                       |

사실대로 답하면 F01(5번)·F02(1~3번)·F05(4번)는 **숫돌 상태 확인에서 멈춘다.** 설계된
차단이다. 멈춘 층과 항목을 적고, 그 전까지 앱이 읽은 값은 값 확인 화면 캡처로 남긴다.

F03·F04에서는 값 확인 화면의 숫돌 종류를 **AI 제안과 상관없이 실물 종류로** 고른다.
사실대로 고르면 규격 대조는 판정불가로 끝나야 한다. AI 제안이 「일반 결합숫돌」이었다면
그 사실을 따로 적는다 — 작업자가 알아채지 못하면 적합으로 넘어갈 수 있는 경로다.
유효기한이 인쇄된 제품이면 규격 대조까지 가고, 없으면 5번에서 멈춘다.
규격 대조 층에서 미지원 종류를 막는 동작은 자동 테스트(`engine.test.ts`)가 합성 값으로
덮는다. **실물로 그 층까지 가지 못했으면 「상태 확인에서 멈춤」으로만 적는다.** 규격
대조 층을 확인했다고 쓰지 않는다.

## 3. 한 세트 진행과 기록

### 3-1. 앱을 켜기 전 — 정답 기록지

정답 기록자가 **실물**을 보고 적는다. 사진을 보고 적지 않는다. 애매하면 두 사람이
따로 읽고, 다르면 실물을 다시 본다.

| 칸                             | 적는 것                                                    |
| ------------------------------ | ---------------------------------------------------------- |
| 표본 ID                        | RC-N01 …                                                   |
| 그라인더 모델                  | 명판 그대로                                                |
| 그라인더 무부하 회전속도 (rpm) | 없으면 `없음`                                              |
| 그라인더 최대 숫돌 지름 (mm)   | 없으면 `없음`                                              |
| 숫돌 최고사용회전속도 (rpm)    | 라벨의 rpm 표기. rpm 없이 m/s만 있으면 §5 식으로 계산한 값 |
| 숫돌 원주속도 (m/s)            | 라벨에 있으면                                              |
| 숫돌 지름 × 두께 × 내경 (mm)   |                                                            |
| 숫돌 용도                      | 절단 / 연삭 / 표기 없음                                    |
| 숫돌 종류                      | 결합숫돌 / 다이아몬드 / 플랩디스크 / 컵휠 / 기타           |
| 유효기한 원문                  | 라벨 그대로 (예: `04/2027`). 없으면 `없음`                 |
| 오늘 작업                      | 절단 / 연삭 — 앱에서 고를 것                               |
| 실물 상태                      | 숫돌 손상·변형, 그라인더 상태 — 사람이 본 대로             |
| **정답 판정**                  | §4 절차로                                                  |
| 촬영 조건                      | 장소, 조명, 날씨, 입력 경로                                |

### 3-2. 앱 조작

1. **표본 전경.** 표본 ID 카드를 실물 옆에 두고 기기 기본 카메라로 한 장 찍는다.
   ID 카드는 **앱으로 찍는 사진에 넣지 않는다** — 라벨 글자와 섞여 판독에 끼어든다.
   갤러리 입력 표본은 파일 이름을 `RC-N04-grinder.jpg`, `RC-N04-wheel.jpg`처럼 붙인다.
2. 메인에서 오늘 작업을 고른다. **이 순간이 소요시간의 시작이다.**
3. 명판을 찍는다. 값 확인 화면이 뜨면 **고치기 전에 캡처한다**(OCR 원본값 증빙).
   「읽어낸 원문 보기」도 펼쳐서 캡처한다.
4. 실물과 대조해 평소처럼 고친다. 값을 직접 확인했으면 「라벨을 직접 보고 위 값을
   확인했습니다」를 켠다. 고쳤는지 기록지에 표시한다. 숫돌 값 확인 화면에서는
   **숫돌 종류도 실물을 보고 고른다.** 「AI 제안」에 적힌 종류를 기록지에 옮겨 적고,
   다르게 골랐으면 그 사실도 적는다. 제안과 다르게 고르면 직접 확인을 체크해야 넘어간다.
5. 그라인더 상태 5항목에 **사실대로** 답한다. 멈추면 화면을 캡처하고 11번으로 간다.
6. 숫돌 라벨을 찍고 3~4를 반복한다.
7. 숫돌 상태 확인 화면에 뜬 경고(손상 의심·라벨·유효기한)를 적는다. 5항목에
   **사실대로** 답한다. 멈추면 캡처하고 11번으로 간다.
8. 결과 화면을 **맨 위부터 끝까지** 캡처한다 — 판정, 검사 항목, 규칙 버전. 라벨에
   인쇄된 표기는 「표기 일치」「유효기한」「장착 규격」 항목에, 작업자가 고른 숫돌 종류는
   「숫돌 종류」 항목에 나온다.
9. 체크리스트 3항목에 사실대로 답한다.
10. 결과가 적합이면 시험운전. 이 점검을 위해 숫돌을 새로 끼웠으면 「예 — 교체 후」,
    아니면 「아니오 — 작업 시작 전」. **실제로 돌린 경우에만** 타이머가 끝난 뒤 답한다.
11. 저장했으면 **저장 직후 기기 시각(초까지)** 을 적고, 이력 화면 맨 위에 방금 기록이
    있는지 본다. 저장하지 않았으면 이유를 적는다(§3-3).
12. 이 세트를 저장하거나 「저장 안 함」으로 적은 뒤에 다음 세트를 시작한다. 두 세트를
    겹쳐 진행하지 않는다.

앱은 한 점검의 명판 사진과 숫돌 사진을 **한 기록에 함께** 저장한다(이력 상세에 나란히
보인다). 표본 ID와 기록을 잇는 것은 저장 시각과 CSV의 `createdAt`·`id`다. 촬영한 뒤
화면을 새로고침하면 값은 남지만 사진은 기록에 남지 않는다 — 1번의 전경 사진과 캡처를
따로 남기는 이유다.

### 3-3. 저장하지 못한 세트

저장되지 않은 세트는 **CSV에도 연구 패널 지표에도 들어가지 않는다.** 기록지에서 따로
센다. 조용히 빠지면 표본 수가 줄어든 줄 모르고 비율만 보게 된다.

| 경우                                          | 기록지에 적는 것                                                                                      |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 상태 확인에서 멈춤                            | `멈춤: 숫돌 상태 5번`처럼 층과 항목                                                                   |
| 적합이지만 시험운전을 실제로 할 수 없음       | `저장 안 함: 시험운전 미실시`. 「이상 없음 확인」을 누르지 않는다                                     |
| **사람의 정답은 부적합인데 앱이 적합을 보임** | `적합 표시(정답 부적합)` — **합격 기준 2 실패.** 시험운전하지 않고 결과 화면을 캡처한 뒤 「처음으로」 |
| 체크리스트를 사실대로 채울 수 없음            | `저장 안 함: 체크리스트 미충족`                                                                       |
| 앱 오류로 진행 불가                           | 오류 화면 캡처, 단계, 문구 — 합격 기준 7 확인 대상                                                    |

### 3-4. 네 가지 값은 어디서 얻나

| 값                | 뜻                                  | 얻는 곳                                                                                                                                                                                                                        |
| ----------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **실제 정답값**   | 사람이 실물을 읽은 값               | 정답 기록지 → 정답 JSON(§5)                                                                                                                                                                                                    |
| **OCR 원본값**    | 사람이 고치기 전에 앱이 읽은 값     | CSV `grinderRPM_ocr` `grinderMaxDiameter_ocr` `wheelMaxRPM_ocr` `wheelDiameter_ocr`. CSV에는 이 넷만 있다. 모델명·두께·용도·유효기한과 AI가 제안한 숫돌 종류는 값 확인 화면 캡처                                               |
| **정규화값**      | 코드가 단위를 바꾼 값               | `wheelMaxRPM_ocr`은 m/s를 rpm으로 **환산한 뒤**의 값이다. 라벨에 인쇄된 원래 표기(rpm·m/s·유효기한 원문·내경)는 CSV에 없어 결과 화면 캡처로 남긴다. 환산했는지 여부도 CSV에 없고, 연구 패널의 단위 정규화 지표 계산에만 쓰인다 |
| **작업자 확정값** | 값 확인 화면에서 확인·보정한 최종값 | CSV `grinderRPM` `grinderMaxDiameter` `wheelMaxRPM` `wheelDiameter` `wheelThickness` `wheelPurpose` `wheelType`(작업자가 고른 종류). 고쳤는지는 `grinderEdited` `wheelEdited` (`Y`/`N`, 숫돌은 종류만 바꿔도 `Y`)              |

### 3-5. 상태 확인은 AI 정답이 아니다

- 그라인더 상태·숫돌 상태 응답은 **작업자가 직접 본 결과**다. 앱이나 AI가 채우지
  않으며 정답 JSON에도 없다.
- CSV `condition…` 열은 작업자 응답 기록이다. 채점하지 않는다. 「AI가 상태를 몇 %
  맞혔다」 같은 수치를 만들지 않는다.
- 사진에서 손상이 보이지 않아도 앱은 **「손상 없음」으로 확정하지 않는다.** AI는
  의심될 때만 경고를 더한다. 경고가 뜨지 않은 것을 「이상 없음」의 근거로 적지 않는다.
- RC-F02에서 손상 의심 경고가 뜨지 않았다면 그대로 적는다. 앱이 약속하는 기능이
  아니므로 합격 기준 실패로 세지는 않지만 숨기지 않는다.

## 4. 정답 판정 절차

정답 판정은 **이 앱의 규칙을 사람이 실물 값에 적용한 결과**다. 작업이 안전한지에 대한
판단이 아니다. 이 절차와 `src/lib/rules/engine.ts`가 다르면 코드가 맞다 — 이 문서를 고친다.

**먼저 부적합, 그다음 판정불가** 순서로 본다.

**① 하나라도 해당하면 `INCOMPATIBLE`**

1. 숫돌 최고사용회전속도 < 그라인더 무부하 회전속도 (같으면 해당 없음)
2. 숫돌 지름 > 그라인더 최대 숫돌 지름 (같으면 해당 없음)
3. 오늘 작업(절단/연삭)과 라벨의 숫돌 용도가 다름
4. 라벨 유효기한이 지남 — 표시된 달의 **말일**까지 유효로 본다. 기준일은 점검 날짜

**② ①에 해당하지 않고, 하나라도 해당하면 `UNDETERMINED`**

5. 그라인더 무부하 회전속도나 숫돌 최고사용회전속도가 없음
6. 그라인더 최대 숫돌 지름이나 숫돌 지름이 없음
7. 라벨에 숫돌 용도(절단/연삭)가 없음
8. 일반 결합숫돌이 아님 (다이아몬드·플랩디스크·컵휠·와이어브러시 등)
9. 유효기한 표시가 없음
10. 원주속도 `v = π × 지름[m] × rpm ÷ 60`이 15 m/s 미만이거나 110 m/s 초과.
    그라인더(최대 숫돌 지름·무부하 회전속도)와 숫돌(지름·최고사용회전속도)을 각각 본다.
    **이 범위는 안전 한계가 아니라 잘못 읽은 숫자를 거르는 범위다.**
11. 라벨에 rpm과 m/s가 둘 다 있는데, rpm을 숫돌 지름으로 m/s로 옮긴 값이 라벨의
    m/s와 10% 넘게 다름

**③ 그 외는 `COMPATIBLE`**

정답 판정에 넣지 않는 것: 인식 신뢰도(모델이 스스로 내는 값), 외관 손상 경고,
장착 규격(내경). 셋 다 라벨의 규격 값이 아니다. 실물 손상은 정답 기록지 「실물 상태」에
따로 적는다.

## 5. 정답 JSON

검증 빌드 이력 화면의 「정답(Ground Truth) 파일」에 넣는 파일이다. **기기별로 하나씩**
만든다. 앱은 형식이 어긋난 줄을 고치지 않고 버리며, 몇 줄 버렸는지 보여준다.

형식(설명용 — 꺾쇠 부분을 실제 값으로 바꿔야 JSON이 된다):

```text
[
  {
    "recordId": <CSV의 id>,
    "grinderRPM": <숫자 또는 null>,
    "grinderMaxDiameter": <숫자 또는 null>,
    "wheelMaxRPM": <숫자 또는 null>,
    "wheelDiameter": <숫자 또는 null>,
    "verdict": <"COMPATIBLE" | "INCOMPATIBLE" | "UNDETERMINED" 중 하나>
  }
]
```

- `recordId` — 기록지의 저장 시각을 CSV `createdAt`과 맞춰 찾은 `id`. 정수.
- 여섯 키를 **모두** 적는다. 키가 하나라도 빠진 줄은 버려진다.
- 숫자는 따옴표 없이 적는다. `"12200"`처럼 적은 줄은 버려진다.
- 라벨에 **애초에 없는** 값은 `null` — 채점에서 빠진다. 읽을 수 있는데 적지 않은 것과 다르다.
- m/s만 표기된 숫돌의 `wheelMaxRPM`은 `내림(m/s × 60 ÷ (π × 지름[m]))`. 앱과 같은
  식이고 **내림**이다(README 「m/s → rpm 환산」).
- **넣지 않는 기록:** 저장되지 않은 세트(애초에 `id`가 없다), §6 기기 시험에서 저장한
  기록. 정답이 없는 기록은 지표 계산에서 빠진다.
- 불러온 뒤 「형식이 맞지 않아 N줄을 제외했습니다」가 뜨면 고쳐서 다시 넣는다.
  제외된 채로 나온 지표를 옮겨 적지 않는다.

## 7. 지표 측정

주 기기 검증 빌드의 연구 패널 값을 **그대로** 옮긴다. 기기를 여러 대 썼으면 기기별로
적고, 합칠 때는 **분자끼리·분모끼리 더한다.** 비율을 평균하지 않는다.

| 지표             | 분자                                                         | 분모                                                              | 얻는 곳                              |
| ---------------- | ------------------------------------------------------------ | ----------------------------------------------------------------- | ------------------------------------ |
| False-Safe Rate  | 정답 `INCOMPATIBLE`인데 저장된 앱 판정이 `COMPATIBLE`인 기록 | 정답 JSON과 짝지어진 저장 기록 (채점 기록)                        | 연구 패널                            |
| 판정불가율       | 앱 판정이 `UNDETERMINED`인 채점 기록                         | 채점 기록                                                         | 연구 패널                            |
| 필드 추출 정확도 | OCR 원본값이 정답과 같은 필드                                | 정답이 `null`이 아닌 필드 (그라인더 rpm·최대 지름, 숫돌 rpm·지름) | 연구 패널(전체), CSV `*_ocr`(필드별) |
| 단위 정규화 오류 | m/s에서 환산한 기록 중 숫돌 rpm이 정답과 다른 것             | m/s에서 환산한 채점 기록                                          | 연구 패널만 — 환산 여부가 CSV에 없다 |
| 점검 소요시간    | —                                                            | 저장 기록                                                         | CSV `elapsedMs`                      |

분모가 0이면 모두 N/A다. 소요시간은 저장 기록이 없으면 N/A다.

- **False-Safe Rate의 분모는 채점 기록 전체다.** 정답이 부적합인 기록 수가 아니다
  (`src/lib/record/metrics.ts`). 정답 부적합 기록 수를 함께 적는다 — 호환 표본이
  많을수록 같은 건수도 비율이 작아 보인다.
- **False-Safe Rate가 보지 못하는 것:** 저장되지 않은 세트, 정답이 `UNDETERMINED`인
  표본(미지원 숫돌 등)이 적합으로 나온 경우. 그래서 합격 기준 2·3을 기록지로 따로 센다.
- **판정불가는 실패가 아니다.** 설계된 동작이다. False-Safe와 맞바꾸지 않는다.
- **필드별로도 적는다.** 연구 패널은 전체 비율만 보여준다. 필드마다 맞음 / 못 읽음
  (빈 값) / 틀림을 CSV `*_ocr`과 정답으로 센다. 틀림이 못 읽음보다 나쁘다.
- **위험 방향으로 틀린 원본값을 따로 센다.** 그라인더 rpm을 낮게, 숫돌 rpm을 높게,
  숫돌 지름을 작게 읽은 OCR 원본값. 사람이 고쳐서 판정이 맞았어도 센다. False-Safe
  0건은 작업자가 값을 고친 흐름의 결과라서, 이 건수 없이 보고하면 인식 성능이 부풀려진다.
- **정정률:** `grinderEdited` 또는 `wheelEdited`가 `Y`인 기록 / OCR 원본이 있는 저장 기록.
- **소요시간은 두 가지로 적는다.** 적합 세트에는 법정 시험운전(60초 또는 180초 이상)이
  들어간다. 전체 `elapsedMs`와 `elapsedMs − trialRunElapsedSeconds × 1000`을 함께
  적는다. 개별값을 모두 싣고 중앙값을 붙인다. 1시간이 넘는 기록은 빼지 말고 표시한다.
- 수기 점검과의 비교는 [validation-plan.md](validation-plan.md) §2를 따른다.

## 9. 실측한 뒤에 정할 것

아래는 **20세트 결과를 보고 정한다.** 지금 기준값을 적지 않는다. 결과가 나오기 전에
목표치를 정하면 결과를 거기에 맞춰 읽게 된다.

- OCR 필드 추출 정확도의 합격선
- 판정불가율의 허용 범위 — 너무 높으면 현장에서 앱을 끄게 된다
- 단위 정규화 오류 — 환산 표본이 한두 건이면 판단을 미룬다
- False-Safe Rate의 분모 — 채점 기록 전체로 볼지, 정답 부적합 기록으로 볼지
- 점검 소요시간 목표 — 법정 시험운전이 들어가면 적합 세트는 60초를 넘는다.
  「30초 사전점검」을 무엇으로 볼지
- 유효기한 표시가 없는 숫돌 — 지금 흐름에서는 상태 확인에서도 규칙엔진에서도 적합으로
  가지 않는다. 현장에서 받아들일 수 있는지
- 판독 곤란 조건별로 재촬영 안내가 필요한지
- Android와 iPhone 사이에 차이가 있는지
